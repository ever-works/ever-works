## Decisions

1. **Names carry the `ActionsRunner` prefix.** `FleetRunner…` already names the sidebar's "is my local runner up?"
   pill (`fleet-runner-status.types.ts`, about Fleet nodes), so every type, constant and helper of this epic is
   `FleetActionsRunner…` / `FLEET_ACTIONS_RUNNER…`; the job payloads keep the plan's `FleetRunnerInstallPayload` /
   `FleetRunnerControlPayload`.
2. **Stored states are CONTRACTS §4.11 revision 6's** (`installing · idle · working · offline · stopped · failed ·
removed · unknown`): "stopped (by you)" is `stopped` with `stoppedByOwner`, a failed install is `failed` with the
   first line in `lastError`. The plan's older encoding (`offline` + flag, `installing` + error) is not used.
3. **The token travels over the node's own authenticated HTTPS call, not a link message.** FR-7 says "over the node
   link"; the node asks `POST /api/internal/fleet/runners/:runnerId/token` with its node credential and the
   `runner-*` job it holds (the `push-credential` posture of FL-16's virtual enrolment token: one undifferentiated
   401, 409 stale-lease, `Cache-Control: no-store`). Reason: the install is a durable job that must survive link
   drops and platform restarts (U11), and the link's operations live in one API replica's memory. The token is still
   minted only when the node is ready (`awaiting-token`), handed over once, protected in the node's logger before the
   call returns, and given to the runner only through `ACTIONS_RUNNER_INPUT_TOKEN` in the child's environment.
   Progress rides the same posture (`…/progress`). Owner question 1.
4. **Queue SLA for the runner jobs is 2 h, not the plan's 1 h / 10 min** — FL-16's decision 2: an unknown kind fails
   closed to the shortest existing default, which these must not undercut.
5. **Refuse before registering.** The node checks the service can be installed (passwordless `sudo -n -l` for the
   runner's `svc.sh` on Linux, elevation on Windows, a service manager at all) after the build is extracted and
   BEFORE it asks for a token, so nothing is registered at GitHub that could not run. A refusal that holds for every
   runner of the install fails them all with the same sentence (the exact command included).
6. **The sudoers command is narrow:** `<user> ALL=(root) NOPASSWD: <runners folder>/*/svc.sh` in
   `/etc/sudoers.d/ever-works-actions-runners` — only the runners' own service script, never a blanket rule.
7. **One download per install.** The archive is fetched and verified once, extracted into each runner's folder, and
   deleted after the last; the checksum is verified while streaming, before any extraction.
8. **Remove order follows the runner build:** Linux / macOS uninstall the service first (the runner refuses to
   deregister while its service is installed), then `config remove` with a one-time remove token; Windows'
   `config remove` takes its service with it (an `sc.exe delete` takes back one it left). When the runner could not
   deregister itself (its folder was gone, `config remove` failed) the node reports `removed` with
   `deregistered: false` and the platform deletes it at GitHub by its id (FR-16). `deregistered` is an additive,
   optional progress field.
9. **Only a folder that carries THIS runner id is touched.** A `runner-control` whose name matches a folder of
   another runner row is refused `invalid`; every path is built from a validated runner name.
10. **The policy helpers are exported by name from the runners barrel**: `capabilityValue` is FL-16's export too, and
    `packages/agent/src/fleet/index.ts` re-exports both folders.
11. **Runner logs are FL-08 sources only under `--manage`** (FL-08's rule for the Logs tab): the `runner:<name>`
    source lists and opens a runner's newest `_diag/Runner_*.log`, resolved by the machine from the name.
12. **Docker mode and reinstall are refused `unsupported_on_node` until P3 ships them**, at the API and on the node.
13. **Web (P1):** the typed-name Remove reuses FL-09's `ConfirmActionDialog` (no separate dialog); failed and unknown
    rows offer Remove only (no Retry until P3's reinstall); viewers outside the `machines` audience see no Install button
    and the row acts disabled with the reason; the Install options are read once per list answer and after an act, not
    on every 30 s refresh; the palette's "Install Actions runners on <computer>" opens the dialog through
    `?runners=install`; the Logs link is FL-08's `?tab=logs&source=runner:<name>`; the Logs viewer names the new
    `runner` source kind (`fleet.logs.kinds.runner`); the copy says "container-isolated", never a product name.

14. **P2 — watched targets are the plugin's user-scope setting** (`watchedTargets`, plan §7), so no migration: FL-18
    has no CONTRACTS §13 slot 01. The plugin's `configurationMode` became `hybrid` for that one non-secret setting
    (still no credential, nothing a person must fill in). An empty saved list means the default (every target the
    person has runners for).
15. **P2 — jobs are read without conditional requests.** The plugin lists queued and in-progress runs separately; a 304
    on one of them would drop its jobs, so the service sends no ETag and leans on its own 30 s cache (5 min off-page
    through the poll) and GitHub's rate-limit back-off. An organisation target reads at most 20 of its installation's
    repositories.
16. **P2 — `job-unassignable` never waits on GitHub.** The producer reads the jobs the panel or the 5-minute poll last
    fetched for the person (the poll now warms them per owner), and places each item on the computer of the first of
    the person's runners registered for the job's repository (or organisation), else on the first computer they have
    runners on; with none visible nothing is raised.
17. **P2 — Cancel workflow run is the person's own runs only.** Every listed job is of a target one of the caller's own
    installations covers, and the cancel resolves the repository through them again; `canCancel` is false while the kill
    switch holds (U14). The audit row has no computer (`nodeId: null`), the run as `target`. An Agent's cancel is held
    for approval like every act (`alwaysHeld` in the catalogue).

18. **P2 web:** the Actions jobs panel is the hub Overview block `fl-18.actions-jobs` (order 110, after FL-01's
    "needs a look"); it renders nothing on a 404 and also when the person has no jobs, no runners, no watched list and
    no unreadable target (no empty box for people who never installed a runner). Cancel shows only with `canCancel`,
    disabled with the reason under the kill switch, through FL-09's confirm loop. `?actionsJob=<owner/repo>#<runId>`
    (the `job-unassignable` route) highlights the run, or says it is no longer queued or running. Picking an
    organisation in the Install dialog runs the permission check first (Install off while it runs; a failed check does
    not block — the server decides) and shows the Grant access card when the permission is missing. The palette's
    "Actions jobs" opens `/fleet#fleet-actions-jobs`. The P1 module spec's "no hub block yet" assertion now pins exactly
    the jobs panel. Queued jobs use ◷.

19. **P3 — the container executor is a capability of its own** (`actions-runner-docker`, CONTRACTS §1.2 addition):
    the node advertises it under `--work` on Linux when the Docker socket exists; Docker-mode jobs require it beside
    `actions-runner`, so an older node never leases a job it cannot run. The API refuses Docker mode elsewhere
    `unsupported_on_node` and never carries the daemon opt-in in service mode.
20. **P3 — the container runs GitHub's verified build, not the image's own.** The node downloads and verifies the build
    exactly as for a service runner and mounts that folder into GitHub's runner image (pinned trust-on-first-use to the
    digest the first pull resolves, kept in the runner's meta), as the node's `uid:gid`. Registration is a `--rm`
    container with `-e ACTIONS_RUNNER_INPUT_TOKEN` and no value (Docker copies it from the CLI's environment), so the
    token is never on argv and never in the long-lived container's configuration. Owner question 5.
21. **P3 — Reinstall = take down + install again** through the same per-runner install (`installOneRunner`): the
    platform hands GitHub's current build for the computer in the `runner-control` payload; the node deregisters with
    a remove token, deletes the folder, then installs with a fresh registration token. The row is `installing` until
    the node reports `idle`. Update available is read from GitHub's build list, cached an hour per target.
22. **P3 — CLI** `ever-works fleet runners list|jobs|install|start|stop|restart|reinstall|remove|cancel-run` over the
    same routes; MCP gained no tool (Reinstall is `fleet_runners_action` with `reinstall`, held for an Agent).
23. **P3 web:** "Container-isolated — each runner in its own container" when offered; the opt-in checkbox carries the
    spec's label verbatim with a one-line warning; a failed row's **Retry** and an update's **Reinstall…** are in-row,
    otherwise Reinstall sits in the row menu above Remove; the P1 shared-spec assertion that pinned the container
    mode off now pins it on (and off when the gate is passed false).
24. **MCP run-token surface:** `fleet_runners_jobs` and `fleet_runners_cancel_run` are refused for fleet-run tokens
    (#2921, beside the lead's #2920 for the four P1 tools); the whitelist total in the MCP README and feature page is
    the real length.

## Questions for the owner

1. **Token transport (decision 3).** FR-7 asks for the registration token "over the node link"; P1 hands it over the
   node's own authenticated HTTPS call (the FL-16 enrolment-token posture) so an install survives link drops. Keep
   it, or move it onto a `runner.token` link message once operations are durable across replicas?
2. **GitHub App permissions.** Repository runners need **Administration: read & write**, organisation runners
   **Self-hosted runners: read & write**. Existing installations created before FL-18 may lack them; the refusal names
   the permission (U8). Should the App manifest request them by default (installations then need a re-approval)?
   (This is `OWNER-QUESTIONS.md` A16; listed here so the lane log is complete.)
3. **Sudoers drop-in (decision 6).** Is the narrow `svc.sh`-only rule the right one-time command for Linux hosts, or
   should the node offer a root-run installer instead?
4. **Removed rows are purged after 30 days** (the audit rows keep the history). Longer?
5. **Container image pinning (decision 20).** Docker-isolated runners run GitHub's runner image pinned
   trust-on-first-use to the digest the computer's first pull resolves (FL-16's catalogue posture). Should the platform
   ship a digest list instead?
6. **The Docker daemon opt-in label** is the spec's own sentence, "Share the Docker daemon (runs as root)" — the one
   place the product name appears in the copy. Keep it?
