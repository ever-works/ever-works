## Decisions

1. **The management lane already existed (FL-02 T-27).** FL-16 is the first epic to register kinds: contracts'
   `FLEET_MANAGEMENT_LANE_KINDS` = `['vm-create', 'vm-control']`, both needing `manage`. The FL-02 specs that pinned
   the list as empty ("until an epic registers a kind") now pin FL-16's two kinds — the test was written to be
   evolved by this epic, and it asserts strictly more than before.
2. **Queue SLA for the VM jobs is 2 h, not the plan's 1 h / 10 min.** Like `computer-session` and `agent-session`,
   they do not undercut the shortest existing default, which is what an unknown kind fails closed to; lowering it
   would change every older reader's answer for an unknown kind.
3. **A `virtual-host` capability tag (additive, CONTRACTS §1.2 question).** Every `vm-*` job requires `managed`,
   `docker` AND `virtual-host`; only a node that runs FL-16's executors advertises the last one. Without it an
   FL-02-era node started with `--work --manage` on a Docker host would lease a `vm-create` through its work lane
   (it does not know the kind is the management lane's) and fail it.
4. **The host resolves the image, the platform never names one.** `vm-create` carries the `systemId` only; the
   node maps it through its OWN catalogue (with operator overrides) and reports the `ref@digest` it used, which is
   stored in `virtualMeta.image` and shown on the child. The host therefore executes only catalogue images even if
   a job payload were forged.
5. **Progress rides the durable job, not a link operation.** The node reports each phase through a node-credential
   internal endpoint (`POST /api/internal/fleet/virtual/:childId/progress`, authorised like `push-credential`:
   the job, its holder, its lease generation) and the platform stores it on the child's `virtualMeta`. The
   `operationId` a create / power / destroy answers is the job id. Reason: a create is a durable job that must
   survive link drops and platform restarts (U9); FL-02 operations live in one API replica's memory and are tied to
   a link request. The hub polls the children every 5 s while one is busy (FR-13).
6. **Image pinning is trust-on-first-use until the owner supplies digests.** The catalogue names a tag per system;
   the first pull on a host resolves the digest and records it in `<node data>/virtual/catalogue.lock.json`, and every
   later create on that host runs `ref@sha256:…`. An operator override (`EVER_WORKS_NODE_VIRTUAL_IMAGE_<SYSTEM>`)
   may name a full `ref@sha256:…`. Owner question 2.

7. **Gate order and the link.** `FleetVirtualService` runs its own gate (existence through FL-01's
   `FleetAccessService`, the kill switch fail-closed, the host's eligibility from the stored consents and tags, the
   request, then the confirmation) instead of the node link's `authorizeRequest`: a create is a durable job and must
   not need `FLEET_NODE_LINK_ENABLED` or a live link at the moment the owner presses Create. The link is used only for
   the reconcile's `vm.list` read (through FL-09's `FLEET_MACHINE_NODE_PORT`).
8. **A child's registration may be removed once nothing can confirm its machine.** FR-29's guard (`unsupported_on_node`,
   "destroy it instead") applies while the host is known and recently seen; it lifts when the child is `gone`,
   `failed` or `not-enrolled`, when the host's registration is gone, or when the host has been silent for 24 h
   (`FLEET_VIRTUAL_ORPHAN_HOST_SILENCE_MS`). Without that, a dead host would leave its children un-removable (destroy
   needs the host, remove refuses, the host's own remove refuses while it has children).
9. **The guest's home is a named Docker volume, the token goes in through `docker exec -i`.** The plan bind-mounted
   `<data dir>/home`; a root guest would then write root-owned files into a host folder the node's (non-root) user
   could not delete on destroy, and the host could not even stat the readiness marker. Instead: home =
   `ew-virtual-<childId>-home` (removed by destroy, kept by a P3 rebuild); markers are read with `docker exec … test -f`;
   the token is written from the host's stdin into the guest's own 0600 file (`guestWriteTokenArgs`, a constant
   script) — it never touches a command line or the host's disk; the guest's `enroll --token-file` reads and deletes
   it and the host removes it again as a belt. The host's `<data dir>/virtual/<childId>/run/` holds only the
   bootstrap (read-only mount) and `meta.json`.
10. **Agent acts are held, not run.** `fleet_virtual_create`, a stop and `fleet_virtual_destroy` call the service
    without the confirmation field (so every refusal — permission, kill switch, host, busy — is the answer), then file
    an Approval titled with the 409's summary; a person's approval runs it (`FleetVirtualProposalListener`). The
    trust-ladder rung (Ask vs Auto, spec S9) is not read yet: every rung behaves as Ask (the safest reading). Start
    (`plain`) runs at once.
11. **Server actions, not BFF routes.** The web follows FL-09's pattern (`app/actions/fleet/virtual.ts` +
    `lib/api/fleet-virtual.ts`) instead of the plan's `app/api/fleet/nodes/[id]/virtual/**` route handlers.
12. **Reconcile = facade + RPC + API cron**, the FL-14 shape (`FleetVirtualReconcileService`,
    `fleet-virtual-reconcile` Trigger task, `FleetVirtualReconcileCronService`), not a dispatcher symbol.
13. **Container runtime install.** glibc systems install the official Node.js build of the host's major line, verified
    against `SHASUMS256.txt`; Alpine installs the distribution's `nodejs` (the official builds are glibc-only). The
    guest installs `ever-works-node@<host version>` (override: `EVER_WORKS_NODE_VIRTUAL_RUNTIME_SPEC`, e.g. a tarball
    URL for a dev build that is not on npm). The guest runs as root inside its container (no user namespace work in
    P1) with `HOME=/home/ever`.

## Questions for the owner

1. **`virtual-host` tag** (decision 3) — please add it to CONTRACTS §1.2 (advertised with `--manage` by nodes that
   carry FL-16's executors), or name the tag you prefer.
2. **Image digests** (decision 6) — may the catalogue ship real digests for the six Container systems (refreshed by
   a release step), or is trust-on-first-use per host acceptable?
3. Spec §8b questions stand with their defaults (password reveal owner-only; children run `--work --manage` without
   `--attend`; Windows images hidden until P2; no per-Container disk quota).
4. **Trust ladder for virtual acts** (decision 10) — should an Agent at the Auto rung create / stop / destroy without an
   Approval (spec S9 says Auto answers 409 until `confirm: true`)? Today every rung is held.
5. **Alpine's Node.js** (decision 13) — the distribution's `nodejs` may be an older major than the host's; acceptable,
   or should Alpine be dropped from the catalogue until an official musl build exists?
