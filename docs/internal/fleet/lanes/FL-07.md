## Decisions

1. **A desktop view is one viewer socket bridged to one `desktop` channel — no new relay.** `POST …/desktop/views`
   checks everything, writes `node.desktop.view`, and mints FL-02's single-use 60-second viewer token for
   `/ws/fleet/desktop/<viewId>`; the channel opens when the browser presents it (FL-02's viewer gateway re-authorises:
   existence → kill switch → consent → the `desktop` audience), and the node — verifying its helper a moment before —
   starts the picture. FL-02's viewer bridge already forwards every node frame (`FRAME`, `TILES`, JSON) and refuses a
   watcher's input, so plan T-22's "relay bridging" is FL-02's existing bridge; nothing new on the relay bus.
2. **P1 views are records per API replica, not `computer_sessions` rows.** The rows (`source`, `displayId`, nullable
   `agentId`, the recording columns) are slot 01, which P2 adds with recording; writing desktop rows before then would
   put `agentId = null` rows in front of the AW-11 services that assume an Agent. The caps still count both sources
   (FR-33): the open `computer_sessions` of the computer / Organization plus the live (or 90-second reserved) desktop
   views on this replica; the node refuses a third Desktop stream itself, so the per-computer cap holds whatever replica
   asked. The per-Organization cap is per replica until P2 (owner question 2).
3. **The eight desktop reasons are their own union** (`FLEET_DESKTOP_REASONS`), with a platform-side `FleetDesktopBlocker`
   list in check order (kill switch, kind, offline, consent, audience, the machine's reasons, the link). The browser
   source's `COMPUTER_UNWATCHABLE_REASONS` is unchanged (FR-12) — widening it would have changed every switch over it.
4. **The Desktop source is not a `CaptureBackend` of the attended lane.** It rides the link's `desktop` family directly
   (`link/modules/desktop/desktop-source.ts`, plugged into FL-02's `createDesktopModule(…, { desktop })`); the browser
   source, its job kind and its legacy leg are untouched. Plan T-14's `CaptureBackend` shape is not needed for watching.
5. **Helper transport in P1 is the helper's own stdin / stdout as a direct child of the node, on every OS.** That works
   when the node runs in the person's session (a terminal, a login item); a node running as a system service has no
   desktop, and the helper says so (`no-display-session` in Windows session 0; no `DISPLAY` on Linux). The plan's
   per-user LaunchAgent + `0600` Unix socket (macOS) and scheduled task + owner-only named pipe (Windows) are
   follow-ups (owner question 5).
6. **Capture paths in P1 are the simplest correct ones**: X11 `GetImage` + XFixes pointer (not XShm), GDI `BitBlt` with
   `CAPTUREBLT` + per-monitor DPI (not DXGI duplication), CoreGraphics `CGDisplayCreateImage` after a Screen Recording
   preflight (not ScreenCaptureKit; deprecated on recent macOS, no pointer — owner question 6). All behind one
   `Capturer` trait. Tiles are diffed at the stream's width (box-average downscale first), each changed 64-px tile
   JPEG-encoded (`jpeg-encoder`), a keyframe on cadence or when most of the picture changed, never more than 512 KiB a
   publish (a batch splits, a keyframe re-encodes lower). The helper exits when its stdin closes.
7. **Verification immediately before every start** (`verifyHelper`): no record → `helper-unadmitted` (file installed)
   or `helper-missing`; the admitted file gone → `helper-missing`; another SHA-256 → `helper-untrusted` (start refused,
   one `verify-failed` event per admission); a `signed` record is refused until signed verification exists (P3) —
   never silently accepted as hash-pinned. While a stream runs the record is re-read every second: removed or replaced
   ends every stream (`revoke`, FR-19).
8. **The manifest is a TS module** (`apps/node/src/core/screen/helper/helper-manifest.ts`): the node package ships
   `dist/` only, so a JSON file beside it would not be published. It is empty until a helper is released (an
   owner-approved step). `helper admit --allow-unpublished` admits a build of one's own, recorded `published: false`
   and shown beside the Reduced trust note (owner question 3).
9. **Admission events reach the audit through the heartbeat.** `helper admit|revoke` (another process) and the node's
   own `verify-failed` append to `helper-events.json` (last 20); every beat carries them; the platform writes one
   `node.helper.*` row per event id (`requestedBy: system:node`, `actorUserId: null` — the platform cannot know who was
   at the keyboard) and remembers the ids in `desktopFacts.seenEventIds` (last 100).
10. **`fleet_nodes.desktopFacts`** (simple-json, slot 00, beside CONTRACTS' `helperTrust`) stores what the heartbeat's
    `helper`, `displays` and `desktopReasons` said. Additive, recorded as CONTRACTS revision 23 (owner question 1).
11. **Watching starts on an explicit click**, never on page load: opening a view is audited and shows the machine's
    whole screen. The token's role is always `viewer` in P1; the viewer may send only FL-02's family view controls
    (`desktop.quality`, `desktop.refresh`, `desktop.displays`). A display switch is `PATCH …/views/:viewId` (audited
    `node.desktop.display.set`) answering a fresh grant the tab re-attaches with.
12. **The viewer gateway observer for the `desktop` family** admits only the person's own view, re-checks the
    `desktop` audience, the flag and the 4-hour ceiling on every ping (a viewer who lost the right is closed `4013`),
    and lets FL-10's preview picture (same family, `source: 'browser'`) through untouched.
13. **The shared view carries `helperTrust` and `desktop`** (FR-17: "Reduced trust" wherever the helper is described;
    FR-27: the `view` audience sees the tab and the reason). The block holds display names and sizes and an 8-digit
    fingerprint prefix — never a hash, a path or a picture.
14. **Screenshot**: `GET …/desktop/screenshot` takes one Steady keyframe on a short-lived channel (audited
    `node.desktop.view`, `purpose: screenshot`). The Agent `fleet_desktop_screenshot` tool is not offered yet: the
    tool runtime would carry the picture as tens of thousands of tokens of base64 text (owner question 4).
    `fleet_desktop_displays` is live (Agent tool + MCP, read-only).
15. **`node.desktop.openUrl` is not added**: the audit vocabulary is guarded lowercase kebab (`fleet-panic.spec.ts`), so
    FL-10's hook will write `node.desktop.open-url` when it lands (CONTRACTS revision 23).
16. **The slot 00 migration's `down` is exact** (drops the index and both columns), per the plan; guarded steps converge.
17. **The helper's CI workflow is `workflow_dispatch` only** (`.github/workflows/screen-helper.yml`, fmt / clippy / test on
    Linux, Windows, macOS; release build on request) and is not a required check. The crate is outside the pnpm and
    turbo graphs (`apps/node/native/*` is no workspace package; `apps/node` ships `dist/` only).
