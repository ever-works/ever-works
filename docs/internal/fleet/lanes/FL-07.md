## Decisions

1. **A desktop view is one viewer socket bridged to one `desktop` channel — no new relay.** `POST …/desktop/views`
   checks everything, writes `node.desktop.view`, and mints FL-02's single-use 60-second viewer token for
   `/ws/fleet/desktop/<viewId>`; the channel opens when the browser presents it (FL-02's viewer gateway re-authorises:
   existence → kill switch → consent → the `desktop` audience), and the node — verifying its helper a moment before —
   starts the picture. FL-02's viewer bridge already forwards every node frame (`FRAME`, `TILES`, JSON) and refuses a
   watcher's input, so plan T-22's "relay bridging" is FL-02's existing bridge; nothing new on the relay bus.
2. **P1 views are records per API replica, not `computer_sessions` rows.** The rows (`source`, `displayId`, nullable
   `agentId`, the recording columns) are slot 01, which P2 adds with recording; writing desktop rows before then would
   put `agentId = null` rows in front of the AW-11 services that assume an Agent. The caps still count both sources
   (FR-33): the open `computer_sessions` of the computer / Organization plus the live (or 90-second reserved) desktop
   views on this replica; the node refuses a third Desktop stream itself, so the per-computer cap holds whatever replica
   asked. The per-Organization cap is per replica until P2 (owner question 2).
3. **The eight desktop reasons are their own union** (`FLEET_DESKTOP_REASONS`), with a platform-side `FleetDesktopBlocker`
   list in check order (kill switch, kind, offline, consent, audience, the machine's reasons, the link). The browser
   source's `COMPUTER_UNWATCHABLE_REASONS` is unchanged (FR-12) — widening it would have changed every switch over it.
4. **The Desktop source is not a `CaptureBackend` of the attended lane.** It rides the link's `desktop` family directly
   (`link/modules/desktop/desktop-source.ts`, plugged into FL-02's `createDesktopModule(…, { desktop })`); the browser
   source, its job kind and its legacy leg are untouched. Plan T-14's `CaptureBackend` shape is not needed for watching.
5. **Helper transport in P1 is the helper's own stdin / stdout as a direct child of the node, on every OS.** That works
   when the node runs in the person's session (a terminal, a login item); a node running as a system service has no
   desktop, and the helper says so (`no-display-session` in Windows session 0; no `DISPLAY` on Linux). The plan's
   per-user LaunchAgent + `0600` Unix socket (macOS) and scheduled task + owner-only named pipe (Windows) are
   follow-ups (owner question 5).
6. **Capture paths in P1 are the simplest correct ones**: X11 `GetImage` + XFixes pointer (not XShm), GDI `BitBlt` with
   `CAPTUREBLT` + per-monitor DPI (not DXGI duplication), CoreGraphics `CGDisplayCreateImage` after a Screen Recording
   preflight (not ScreenCaptureKit; deprecated on recent macOS, no pointer — owner question 6). All behind one
   `Capturer` trait. Tiles are diffed at the stream's width (box-average downscale first), each changed 64-px tile
   JPEG-encoded (`jpeg-encoder`), a keyframe on cadence or when most of the picture changed, never more than 512 KiB a
   publish (a batch splits, a keyframe re-encodes lower). The helper exits when its stdin closes.
7. **Verification immediately before every start** (`verifyHelper`): no record → `helper-unadmitted` (file installed)
   or `helper-missing`; the admitted file gone → `helper-missing`; another SHA-256 → `helper-untrusted` (start refused,
   one `verify-failed` event per admission); a `signed` record is refused until signed verification exists (P3) —
   never silently accepted as hash-pinned. While a stream runs the record is re-read every second: removed or replaced
   ends every stream (`revoke`, FR-19).
8. **The manifest is a TS module** (`apps/node/src/core/screen/helper/helper-manifest.ts`): the node package ships
   `dist/` only, so a JSON file beside it would not be published. It is empty until a helper is released (an
   owner-approved step). `helper admit --allow-unpublished` admits a build of one's own, recorded `published: false`
   and shown beside the Reduced trust note (owner question 3).
9. **Admission events reach the audit through the heartbeat.** `helper admit|revoke` (another process) and the node's
   own `verify-failed` append to `helper-events.json` (last 20); every beat carries them; the platform writes one
   `node.helper.*` row per event id (`requestedBy: system:node`, `actorUserId: null` — the platform cannot know who was
   at the keyboard) and remembers the ids in `desktopFacts.seenEventIds` (last 100).
10. **`fleet_nodes.desktopFacts`** (simple-json, slot 00, beside CONTRACTS' `helperTrust`) stores what the heartbeat's
    `helper`, `displays` and `desktopReasons` said. Additive, recorded as CONTRACTS revision 23 (owner question 1).
11. **Watching starts on an explicit click**, never on page load: opening a view is audited and shows the machine's
    whole screen. The token's role is always `viewer` in P1; the viewer may send only FL-02's family view controls
    (`desktop.quality`, `desktop.refresh`, `desktop.displays`). A display switch is `PATCH …/views/:viewId` (audited
    `node.desktop.display.set`) answering a fresh grant the tab re-attaches with.
12. **The viewer gateway observer for the `desktop` family** admits only the person's own view, re-checks the
    `desktop` audience, the flag and the 4-hour ceiling on every ping (a viewer who lost the right is closed `4013`),
    and lets FL-10's preview picture (same family, `source: 'browser'`) through untouched.
13. **The shared view carries `helperTrust` and `desktop`** (FR-17: "Reduced trust" wherever the helper is described;
    FR-27: the `view` audience sees the tab and the reason). The block holds display names and sizes and an 8-digit
    fingerprint prefix — never a hash, a path or a picture.
14. **Screenshot**: `GET …/desktop/screenshot` takes one Steady keyframe on a short-lived channel (audited
    `node.desktop.view`, `purpose: screenshot`). The Agent `fleet_desktop_screenshot` tool is not offered yet: the
    tool runtime would carry the picture as tens of thousands of tokens of base64 text (owner question 4).
    `fleet_desktop_displays` is live (Agent tool + MCP, read-only).
15. **`node.desktop.openUrl` is not added**: the audit vocabulary is guarded lowercase kebab (`fleet-panic.spec.ts`), so
    FL-10's hook will write `node.desktop.open-url` when it lands (CONTRACTS revision 23).
16. **The slot 00 migration's `down` is exact** (drops the index and both columns), per the plan; guarded steps converge.
17. **The helper's CI workflow is `workflow_dispatch` only** (`.github/workflows/screen-helper.yml`, fmt / clippy / test on
    Linux, Windows, macOS; release build on request) and is not a required check. The crate is outside the pnpm and
    turbo graphs (`apps/node/native/*` is no workspace package; `apps/node` ships `dist/` only).

18. **P2: a Desktop view is a `computer_sessions` row** (`source: 'desktop'`, `agentId` null, `userId` = the computer's
    owner so AW-11's lock lookup finds the machine, `openedByUserId` = the viewer). It is written `live` from the start
    (never `requested`, so no node claims it as an AW-11 job) and stamped from the node's `desktop.stats` every 15 s
    (frames, bytes, `lastFrameAt`), so AW-11's 45-second stall rule sees it alive. The caps count rows on every replica
    (owner question 2 closed). Without a row store (a test double) a view stays replica-only, as in P1, so the P1 specs
    hold unchanged. Slot 01's `down` keeps `agentId` nullable (a desktop row would make the rollback fail).
19. **The arbiter takes a Desktop actor** (`ComputerControlActor.source: 'desktop'`): its row is found by who opened it
    (`findDesktopViewFor`), so an Organization member in the `desktop` audience acts from their own view; every other
    rule is AW-11's. Desktop rows audit `node.desktop.control.take|release|request` (never also `computer.*`); a request
    is audited for desktop rows only (AW-11 never audited one).
20. **Control needs the owner's permission ON the machine** (`ever-works-node helper control allow`, typed `control`,
    `helper-control.json`, bound to the admission's `acknowledgedAt`): default off; approving the helper again turns
    it off; `helper control deny` ends a live control within a second (the host re-reads it with the admission record).
    Beyond the spec (owner question 9) — the brief asks for control that is explicit, visible on the machine and
    revocable.
21. **The machine half rides inside the heartbeat's `helper`** (`control`, `inputReasons`) — no new top-level heartbeat
    field, so no new strip tier and no fixture change; a status without `control` (an older node) reads as not allowed.
22. **A take is class `confirm`** (`confirm: true`, else 409 `confirmation_required`); request, give back, keep, extend
    and hand-over are `plain`. Refusals before the arbiter (kill switch, the machine half) are audited
    `node.desktop.control.take|request` with `outcome: 'refused'`.
23. **A `driver` grant goes only to the holder** (`mode: 'controlling'`, `controlledBy` = the username). The node refuses a
    controlling open it cannot serve, drops `INPUT` on a watching channel, refuses the blocked shortcuts itself before
    the helper does, prints who is controlling on its console (and when it ends), and releases every key and button on
    every end (close, kill switch, withdrawal, helper stop).
24. **Driver sockets**: admitted only while the view holds the lock; every ping acknowledges the hold; input pushes the
    idle deadline every 5 s; a drop gives control back after AW-11's 30-second grace unless the view took it again; a
    release on this replica closes its drivers at once (`FleetLinkViewerGatewayService.closeViewers`, an additive FL-02
    method), elsewhere at the next ping. Same per-replica grace as AW-11 (owner question 12).
25. **A controlling channel refuses `desktop.setDisplay`** — FL-02 leaves a `desktop` driver's JSON open
    (`FLEET_LINK_DRIVER_JSON_TYPES` has no `desktop` row and its spec pins that), so the node keeps the display switch on
    the audited `PATCH`.
26. **The `input` tag comes from the helper's tags module** when the admitted helper can inject and control is allowed;
    it is non-selectable (the two opt-ins are the opt-in). The browser injector does not advertise it (owner question
    11); the stale "nothing injects" comment is gone.
28. **A second reader's review** (before merge) closed: blocked shortcuts split across presses (all three layers track
    held modifiers; text refused under Ctrl / Alt / system key); a driver closed as soon as input shows its hold ended on
    another replica (hold re-read at most every second), re-checked after its channel opened, failing closed when the
    hold cannot be read; a person who loses access gives back the hold (`revoked`) at the next ping or act (keep,
    extend, hand-over and the control read are gated too); the disconnect grace releases only when no driver of the
    view came back on any replica (`controlDriverAt`) and never withdraws a request; a request needs `confirm` (a
    hand-over gives control); the receiver of a hand-over re-attaches as a driver; driver grants re-check the machine
    half; the caps and the row are written under AW-11's admission lock; a cached view re-reads its row every 10 s;
    only `INPUT` frames count as input; a helper without `hello.inputReasons` cannot be controlled; input waits for
    the fallback display's first picture; the console prints the username, never an email.
27. **Helper input** (`src/input/`): the injector opens on the first input only (a watched helper never asks the OS for
    input); X11 XTest, Windows `SendInput` + `SetCursorPos`, macOS Quartz events after the Accessibility preflight
    (`hello.inputReasons`); pointer mapped from picture pixels onto the display (FR-38); a refused input is answered
    `inputResult` with a code, never the OS's words.

2. The per-Organization view cap is counted per API replica in P1 (decision 2); P2 moves views to `computer_sessions`
   rows. Acceptable until then?
3. `helper admit --allow-unpublished` (decision 8): admit a helper the owner built themselves (recorded and shown as
   unpublished), or require a fingerprint the node package publishes?
4. The Agent screenshot tool (decision 14): wait for image content in the tool runtime, or offer it now returning only
   the picture's size (no pixels)?
5. Helper launch into the interactive session when the node runs as a service (decision 5): build the LaunchAgent /
   scheduled-task launchers next, or keep "start the node in your session" as the documented requirement?
6. macOS capture (decision 6): move the helper to ScreenCaptureKit (`objc2` bindings) before anyone uses it on macOS 15+?
7. Who builds, signs and publishes helper releases and fills the manifest's fingerprints (an owner-approved release
   step), and when may `screen-helper.yml` run on `stage` / `main` like the job launcher's workflow?
8. FR-17 (a `helper-untrusted` "needs a look" item) beside FL-03's hash-pinned item: P1 adds a second item rather than
   changing FL-03's; merge them?
9. The on-machine control permission (decision 20): keep it as a second, required opt-in, or rely on `--attend` and the
   `desktop` audience alone as the spec does?
10. "Visible on the machine": P2 prints who is controlling on the node's console. Build a native on-screen indicator
    (a tray icon / border) in the helper next?
11. FR-40's other half: advertise `input` for the browser injector too? It flips FL-02/AW-11's
    `capabilities.spec.ts` "never advertises input" test, so it is not done additively.
12. A controller whose socket reconnects to ANOTHER API replica within 30 s may lose control to the first replica's
    grace timer (AW-11 has the same per-replica grace). Acceptable, or move the grace to the lock's acknowledgement?
14. A helper that crashes while a person holds keys leaves them held (only the helper knew what it pressed; it is
    built `panic = abort`). Add a blind release of the modifier keys and buttons when a fresh helper starts after a
    crash during control?
13. Control ships before recording (FR-48: "a view MUST be recorded whenever it enters control mode"); the flag is off.
    Acceptable until the recording PR lands?
