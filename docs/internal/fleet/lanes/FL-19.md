## Decisions

1. **One catalogue in contracts** (`packages/contracts/src/fleet/fleet-tools.types.ts`, `FLEET_TOOL_CATALOGUE`): every
   row of plan §9.1 with name, family, verb, annotation, AW-24 category, CONTRACTS §2.1 permission family, flag, owner
   epic, phase, `status: live | planned`, route, CLI verb, `waitable`, `alwaysHeld`. A family epic flips its rows to
   `live` when it lands — that is the registration point for the three surfaces.
2. **The gate is the published rule, not a second enforcement point.** Steps 1–6 (stop switch, pauses, grants, ladder,
   caps) are AW-24's safety gate that the run loop already asks before every tool call; FL-19 makes it see every fleet
   tool by spreading `fleetToolEntryPointCategories()` FIRST into `ENTRY_POINT_CATEGORY` (an entry an owner epic wrote —
   FL-12, FL-14 — still wins). Steps 7–8 (audience, consent) are the family services' own checks with the Agent's owner
   as caller. `decideFleetToolCall` (`packages/agent/src/fleet/fleet-tool-gate.ts`) states the rule as a pure truth
   table; the Capabilities view and the tests use it.
3. **Holds never outrank a refusal.** A hold (Ask / Draft / `alwaysHeld`) lets the later gates run; an audience or
   consent refusal then wins, so no Decision is created that nobody in the audience could approve (FR-9, S5).
4. **Reads skip the stop switch, the pauses, the ladder and the caps** (U3, FR-2) but still need grant, audience and
   consent (U2).
5. **Decoration at the one assembly point.** `buildDomainTools` maps every descriptor through `decorateFleetTool`:
   catalogue annotation, the no-credits sentence (FR-25), every string of a result through `redactSecrets`, free-text
   refusals lifted to `{ error: { code, hint } }`, throws typed. `list_fleet_nodes` and non-catalogue tools untouched.
6. **`fleet_nodes_list` reads `listVisibleForUser`** (own + Organization-shared, with the role); `scope: own` narrows.
7. **`fleet_status` composition is pure** (`packages/agent/src/fleet/fleet-status.ts`); the API's `FleetStatusService`
   does the four reads (each degrades alone: needs-a-look → `needsALookPartial`, stop switch → `unverified`, sessions →
   `null` while `FLEET_SESSIONS_ENABLED` is off) and is bound under `FLEET_STATUS_READER` for the Agent tool.
8. **`GET /api/fleet/operations`** (new, additive — CONTRACTS §11.2 lists only `/operations/:id`) backs
   `fleet_operations_list` / `fleet operations list` from the same per-replica registry `get` reads. Question Q3.
9. **FL-08's Agent log tools file was never on develop.** `packages/agent/.gitignore` ignores every folder named
   `logs`, so `packages/agent/src/fleet/logs/agent-fleet-logs-tools.ts` stayed untracked while `agent-tool.service.ts`
   and the fleet barrel imported it. Restored verbatim from the FL-08 worktree and un-ignored (`!src/fleet/logs/`).
10. **`FleetLogsApiModule` is now `@Global()`** so `FLEET_LOGS_READER` reaches the api-side `AgentsModule` (the other
    family API modules already are). Health, logs, status and operations are appended LAST to the positional
    `AGENT_DOMAIN_TOOL_SOURCES` inject list, each optional; logs only while `FLEET_MACHINE_FACTS_ENABLED`, operations
    only while `FLEET_NODE_LINK_ENABLED`.
11. **The Capabilities catalog harness lists every fleet family** (stub sub-sources, a tunnel stub that answers "on");
    `agent-tool-catalog.spec.ts`'s independent assembly mirrors it (it had also lacked the sessions and commands
    bundles the harness had).
12. **Confirmation interceptor** (`apps/api/src/fleet/tools/fleet-confirmation.interceptor.ts`): the family service
    still decides whether a call is confirmed (it alone knows the target name and the node's warning, evaluated on
    every call); the interceptor fills `details.class` from the route's catalogue row, words the hint, and drops
    token-style fields. P1 ships it; P2 applies it to the family controllers.
13. **CLI:** one envelope (`fleet-output.ts`), exit map from the contract (`fleet-exit.ts`), the CONTRACTS §2.2 fields
    from flags (`fleet-confirm.ts`: `--yes`, `--confirm-name`, `--ack-blast-radius`, `--no-wait`; asked once on a TTY,
    never for `confirm-destructive`), `runFleetVerb` (`fleet-client.ts`). Computers are named by id or name (`--on`).
    The singular `session` group gains the plural alias (CONTRACTS §11.3) and `read`; `commands` gains `list`, `get`;
    `fleet tools` prints the catalogue locally (no sign-in).
14. **MCP:** read entries for status, health, needs-a-look, services, processes, Docker lists, operations.
    `fleet_nodes_list|get` are NOT added — the legacy `list_fleet_nodes` / `get_fleet_node` already expose those routes
    (FR-3); `fleet_ports_preview_open` stays off (FL-10 U15). `whitelist-fleet.spec.ts` pins the parity.
15. **Run tokens:** every fleet tool not granted to `ew_run_…` tokens is now named in the run-surface spec's refusal
    list (checkouts, logs, commands, ports and the FL-19 reads had been in neither bucket). Question Q1.
16. **Capabilities block:** `GET /api/fleet/tools/gate?agentId=` → `FleetToolsGateView` (per family: read, act rung,
    refusing gate, reason, fix route, live / planned tools, per-computer audience + consent). The Agent's grant matrix
    is resolved once (`ToolGrantEnforcer.resolve`), the ladder once (`AutonomyGrantService.resolve`); an unenforced
    shipped default reads Auto (AW-24 P1 posture). Fix routes: Safety → the Agent's Settings tab (the web has no AW-24
    Safety route yet — Q4), grants → Capabilities, stop switch → Settings → Fleet, audience / consent → the computer's
    Settings tab.

17. **P2 — a held fleet act becomes a Decision.** AW-24's ladder holds a call in the run loop before the tool runs
    (its P1 files nothing). For a catalogued, state-changing fleet tool `AgentRunService.evaluateSafety` now asks
    `FLEET_HELD_CALL_FILER` (API `FleetHeldCallService`) to file ONE proposal — `actionType: 'other'`,
    `payload.kind: 'fleet-tool-call'` (the shape FL-09 already uses for its held acts; CONTRACTS R-33 names
    `fleet_machine_action` — Q6), `humanDecisionRequired`, de-duplicated per (Agent, tool, args, hour) — and the
    tool answers `{ held, decisionId, hint }`. The payload is platform-written: the model's arguments minus the
    confirmation fields, `raisedAt`, the rung, the class and a summary sentence.
18. **Approval runs exactly that call** (`FleetHeldCallListener`, agent side): a person's approval only; the Agent and
    owner re-checked; older than 24 h → nothing runs (spec U12 default); the stop switch re-checked NOW; the call
    goes through the Agent's own `resolveGrantedTools`, so a grant revoked since, a family switched off, or a
    computer's audience refuses it exactly as in a run; the approval supplies `confirm` and the blast-radius
    acknowledgement (a typed `confirmName` only if the Agent sent one). Anything that did not run files an Inbox
    notice. A held fleet call is decided individually (server `requiresIndividualDecision` + the web bulk filter).
19. **Double approval for self-holding families** (Q7): `fleet_commands_run` (FL-12) and `fleet_docker_run` /
    blast-radius machine acts (FL-09) file their own approval when they run, so an Ask-rung hold of one of those
    yields two Decisions in sequence. Built as is (the safe reading: two people-moments, never zero).
20. **`fleet_nodes_wake`** runs FL-03's own wake handler as the Agent's owner (`FleetWakeToolAdapter` resolves
    `FleetHealthController` lazily through `ModuleRef`) — none of the wake rules are copied.
21. **`fleet_operations_cancel`** (registry `requestCancel`) and **`fleet_nodes_git_identity_get|set`** (FL-15's
    `FleetGitIdentityService` with the Agent as caller; set is class `confirm` and owner-only) are new Agent tools;
    `FleetToolsApiModule` imports and re-exports `FleetGitModule` so the api-side tool sources reach the service.
22. **The confirmation interceptor is on every family controller** (services, processes, Docker, sessions,
    commands, checkouts, ports, previews, git identity).
23. **MCP acts:** services action, processes signal, container / image / Compose actions, wake, git identity set,
    operations cancel. `fleet_docker_run` stays off MCP (a run may carry secret values a person types — FL-09 Q5).
    Every one is refused to run tokens.
24. **CLI acts:** `services action`, `processes signal`, `docker container|pull|image-remove|prune|compose-action`,
    `ports open|preview-close`, `sessions end|rename`, `nodes wake|git-identity-set`, `commands cancel`,
    `operations cancel`. T-14 (`fleet_sessions_question|answer`, the CLI `question` / `answer`) shipped with FL-05 P2.
25. **`requestedBy`** — `fleet-requested-by.ts` is the helper; every family already stamps `agent:<id>` for an
    Agent caller (FL-09 `describeFleetMachineCaller`, FL-14, FL-12). Threading the Decision id into the family's own
    audit row needs a field on each family's actor — follow-up, Q8.

26. **P3 doc:** `docs/features/fleet-agent-tools.md` (sidebar after Virtual computers; linked from the MCP server and
    Fleet pages) — the tools, the three gates and their refusals, Decisions for held acts, confirmations without
    tokens, long operations, MCP, the CLI contract, `fleet_status`.
27. **Shell completion** (`ever-works completion <bash|zsh|fish>`, `apps/cli/src/commands/fleet/completion.ts`) is
    generated from the registered commander tree, so it lists exactly the verbs that exist (zsh via bashcompinit).
28. **Palette:** "Fleet tools for this Agent" while an Agent's pages are open (the palette has no list of Agents to
    name each one), linking to the Capabilities block (`#fleet-tools`); hidden with the hub off.
29. **Registration points worked:** the FL-11 and FL-16 lanes flipped their own catalogue rows to `live` (and aligned
    routes) while FL-19 P2 was open. FL-17 (cloud), FL-18 (runners) and FL-20 (usage) have not landed: their rows stay
    `planned` — each epic flips its rows, adds `<family>.ts` to the CLI group (see the comment in
    `apps/cli/src/commands/fleet/index.ts`), its MCP entries (the parity spec then requires them) and its run-token
    refusals. `fleet_usage_get` (FR-25) arrives with FL-20.
30. **`fleet sessions attach --drive`** is accepted (spec FR-22's name); FL-04's default (drive unless `--watch`) is
    kept — Q9.

## Questions for the owner

1. **Run-token fleet reads.** `whitelist-fleet-run-surface.spec.ts` asserts every fleet GET on the MCP whitelist is
   granted to fleet-run tokens, while FL-04 (sessions), FL-08, FL-10, FL-12, FL-14 and now FL-19 refuse theirs (machine
   state of every computer the owner has). The assertion has been red since FL-04 P2. Default built: refuse, and the
   test is left as it is (not weakened). Narrow that assertion to the legacy reads, or grant some reads (status,
   health) to run tokens?
2. **Held fleet acts at the Ask rung (P2).** AW-24's ladder holds a call in the run loop before the tool runs, and its
   P1 files no Decision. FL-19 P2 files an `agent_action_proposals` row (`fleet_machine_action`) for a held fleet tool
   so the owner can approve it; an approval more than 24 h old answers `confirmation_required` (spec U12 default).
   Keep 24 h?
3. **`GET /api/fleet/operations`** is new (not in CONTRACTS §11.2). Add it to the contract, or keep the list Agent/CLI
   only?
4. **No AW-24 Safety tab route on the web.** Ladder and pause refusals link to the Agent's Settings tab. Point them
   elsewhere once a Safety screen ships?
5. **Wait cap.** Family adapters already answer `{ operationId }` when the node replies with an operation (FL-02's 5 s
   inline window); FL-19 does not wrap tools in a second 25 s race. Wanted as well?

6. **R-33's `actionType`.** CONTRACTS R-33 says held fleet acts are `actionType: 'fleet_machine_action'`; develop's FL-09
   files `actionType: 'other'` + `payload.kind`, and FL-19 follows it (`fleet-tool-call`). Add the action type (an
   enum value, no migration) and move both, or amend R-33?
7. **Two Decisions for self-holding acts** (decision 19) — acceptable, or should an Ask-rung hold skip the family's
   own approval once a person approved the FL-19 Decision?
8. **Decision id in family audit rows** (decision 25) — wanted on every family's row, or is the proposal's own record
   (it names the run and the payload) enough?
