## Decisions

1. **No new job kind, no node-side module.** A cloud computer is created by the platform calling the provider (not by a
   node), so there is no management-lane job; the machine runs the ordinary runtime (`start --work --manage`).
2. **Create answers before the provider does.** The registration (status `enrolling`, `origin: cloud`, provider facts,
   a one-time token whose hash alone is stored) is written first; the provider call runs in the background and records
   the machine ref, or the provider's first line as `failed`. A create the provider never answered is marked `failed`
   by the bootstrap watch after 10 minutes (a machine, if one was made, carries the Node tag; P3's unclaimed scan finds
   it). `operationId` is the Node id (the row carries the phase) — FL-16 lane decision 5's reasoning.
3. **The token rides in user data, single-use, 15 minutes** (plan §11 residual risk, unchanged). Cloud-init writes it
   to `/run/ever-works/enroll-token` (tmpfs, 0600); `enroll --token-file` (FL-16's option, reused) reads and deletes
   it; the bootstrap never puts it on a command line.
4. **The bootstrap writes the systemd unit itself.** The published `ever-works-node` ships only `dist/`, so
   `$(npm root -g)/ever-works-node/packaging/` does not exist on a machine. The unit is the shipped template with
   `ExecStart=… start --work --manage` (no `--attend`).
5. **Destroy removes the registration once the provider accepted the delete** (204 deleted, 404 already gone); the
   audit row carries the final cost.
6. **Agent acts are always held.** `fleet_cloud_create`, a power change and `fleet_cloud_destroy` run the whole chain
   without the confirmation field and file an Approval titled with the Decision text (size, region, price); a person's
   approval runs it (`FleetCloudProposalListener`) with every gate again — the price included, so an approval for a
   price that changed is refused `invalid`. The trust-ladder rung is not read yet (every rung behaves as Ask), FL-16
   decision 10's reading. On MCP the three acts are in `MCP_PRIVILEGED_TOOLS` (off by default).
7. **Plugin usage is not recorded.** Cloud spend is the provider's bill on the owner's account, not platform spend, and
   must never reach model-spend Budgets (FR-24); the facade writes no `plugin_usage_events` row (plan §7's "units only"
   would need a new enum value with no reader).
8. **Retry enrolment answers `unsupported_on_node`** for the first provider: its user data cannot be replaced on a
   running machine, so a fresh token cannot reach it; Destroy and create again is the fix (spec U3's "else Destroy").
9. **Organization binding (FR-14)** takes an optional `organizationId` on create; the web dialog does not send one yet
   (owner question 3).
10. **Catalogue rows corrected by the owner epic.** `fleet_cloud_destroy` is `POST /api/fleet/cloud/{id}/destroy`
    (plan §5); FL-19's `DELETE /api/fleet/cloud/{id}` answers the same as an alias. `fleet_cloud_idle_policy` stays
    `planned` until P2.
11. **Software presets in P1:** Docker, Node.js, Claude Code, Codex. The overlay-VPN client is offered only when the
    operator configured its install script (`FLEET_CLOUD_OVERLAY_VPN_INSTALL_URL`; P3 wires the one-time key) — the
    platform names and picks no VPN vendor.
12. **The provider is never named in core.** `machine-provider.facade.guard.spec.ts` walks the core trees and fails on
    any mention outside the plugin package; user copy reads the plugin's own `providerName`.

## Questions for the owner

1. **Runtime pin.** The bootstrap installs `ever-works-node@0.2.7` (`FLEET_CLOUD_DEFAULT_RUNTIME_VERSION`) unless
   `EVER_WORKS_NODE_CLOUD_RUNTIME_SPEC` names another. Should a release step bump it, or should it follow the platform's
   own version?
2. **Spec §8b defaults stand:** OAuth client id / secret as admin-scope settings with env fallbacks (P3); the
   overlay-VPN key is create-time only, never stored.
3. **Organization binding (FR-14):** which Organization is the owner "acting in" on the web — is there a workspace
   scope the dialog should send? Today a cloud computer is created personal (`organizationId: null`) unless a caller
   sends one.
4. **Agent at the Auto rung** (spec S9 says Auto answers 409 until `confirm: true`): today every rung is held for
   approval, like FL-16. Keep?
