## Decisions

1. **No new job kind, no node-side module.** A cloud computer is created by the platform calling the provider (not by a
   node), so there is no management-lane job; the machine runs the ordinary runtime (`start --work --manage`).
2. **Create answers before the provider does.** The registration (status `enrolling`, `origin: cloud`, provider facts,
   a one-time token whose hash alone is stored) is written first; the provider call runs in the background and records
   the machine ref, or the provider's first line as `failed`. A create the provider never answered is marked `failed`
   by the bootstrap watch after 10 minutes (a machine, if one was made, carries the Node tag; P3's unclaimed scan finds
   it). `operationId` is the Node id (the row carries the phase) — FL-16 lane decision 5's reasoning.
3. **The token rides in user data, single-use, 15 minutes** (plan §11 residual risk, unchanged). Cloud-init writes it
   to `/run/ever-works/enroll-token` (tmpfs, 0600); `enroll --token-file` (FL-16's option, reused) reads and deletes
   it; the bootstrap never puts it on a command line.
4. **The bootstrap writes the systemd unit itself.** The published `ever-works-node` ships only `dist/`, so
   `$(npm root -g)/ever-works-node/packaging/` does not exist on a machine. The unit is the shipped template with
   `ExecStart=… start --work --manage` (no `--attend`).
5. **Destroy removes the registration once the provider accepted the delete** (204 deleted, 404 already gone); the
   audit row carries the final cost.
6. **Agent acts are always held.** `fleet_cloud_create`, a power change and `fleet_cloud_destroy` run the whole chain
   without the confirmation field and file an Approval titled with the Decision text (size, region, price); a person's
   approval runs it (`FleetCloudProposalListener`) with every gate again — the price included, so an approval for a
   price that changed is refused `invalid`. The trust-ladder rung is not read yet (every rung behaves as Ask), FL-16
   decision 10's reading. On MCP the three acts are in `MCP_PRIVILEGED_TOOLS` (off by default).
7. **Plugin usage is not recorded.** Cloud spend is the provider's bill on the owner's account, not platform spend, and
   must never reach model-spend Budgets (FR-24); the facade writes no `plugin_usage_events` row (plan §7's "units only"
   would need a new enum value with no reader).
8. **Retry enrolment answers `unsupported_on_node`** for the first provider: its user data cannot be replaced on a
   running machine, so a fresh token cannot reach it; Destroy and create again is the fix (spec U3's "else Destroy").
9. **Organization binding (FR-14)** takes an optional `organizationId` on create; the web dialog does not send one yet
   (owner question 3).
10. **Catalogue rows corrected by the owner epic.** `fleet_cloud_destroy` is `POST /api/fleet/cloud/{id}/destroy`
    (plan §5); FL-19's `DELETE /api/fleet/cloud/{id}` answers the same as an alias. `fleet_cloud_idle_policy` stays
    `planned` until P2.
11. **Software presets in P1:** Docker, Node.js, Claude Code, Codex. The overlay-VPN client is offered only when the
    operator configured its install script (`FLEET_CLOUD_OVERLAY_VPN_INSTALL_URL`; P3 wires the one-time key) — the
    platform names and picks no VPN vendor.
12. **The provider is never named in core.** `machine-provider.facade.guard.spec.ts` walks the core trees and fails on
    any mention outside the plugin package; user copy reads the plugin's own `providerName`.
13. **(P2) An Agent's idle-policy change is held too.** The catalogue class is `plain` / not destructive, but the policy
    decides when the platform powers a billed machine off (or stops telling the owner), so `fleet_cloud_idle_policy`
    runs `FleetCloudService.previewIdlePolicy` (every gate, no write) and files an Approval titled "Change fra-nina's
    idle policy from Tell me after 3 h to Power off after 2 h…"; the approval runs `setIdlePolicy`. On MCP it is
    privileged (off unless `MCP_PRIVILEGED_TOOLS=true`) and refused to fleet-run tokens.
14. **(P2) A policy change restarts the idle window** (and clears the window's dedup key), so the new policy waits its
    full hours from the save — switching to "power off after 1 h" on a machine idle for 5 h never powers it off the
    moment it is saved. "Keep running" restarts the window too, and is audited `node.policy.change`
    (`act: 'keep-running'`).
15. **(P2) The cost model is the contracts' `fleetCloudCost`** (P1 put it there so the web and the agent share it):
    per second, capped at the monthly price per calendar month (UTC), billed only while running at a provider that does
    not bill powered-off machines. T-23's "cost-model.ts" is that function; no second copy in the agent.
16. **(P2) The sweeps write onto the freshest row.** `patchMeta` re-reads the node before writing `providerMeta`, so a
    power act or a policy change a person made between the sweep's list read and its write is kept. The cost job is
    compare-and-set on `cost.computedAt` (a snapshot younger than five minutes, or one another pass wrote meanwhile, is
    left alone); the idle power-off re-checks "running, nothing pending, this window not acted on" before the provider
    call.
17. **(P2) The provider's own month-to-date figure** is read once per provider + owner (with all that owner's machine
    refs) and stored on each machine's cost snapshot; the usage block shows it only for the caller's own machines — a
    machine shared through an Organization never shows its owner's account-wide bill.
18. **(P2) The idle job reads only the samples since its last pass** (20 minutes back, never before the window
    opened): every earlier sample of an open window was already judged flat, or the window would have closed. A
    session in `starting` / `working` / `needs_you` keeps the machine busy (`idle` and `done` do not); a powered-off,
    pending, failed or still-enrolling machine is never idle; a `nothing` policy keeps no window.
19. **(P2) The Cloud computers usage block mounts on the hub Overview** (`registerOverviewBlock`, surface `hub`, order 130) because FL-20's Usage tab is being built in parallel tonight (lane O1). FL-20 mounts the same
    `components/fleet/cloud/CloudUsageBlock` below its model-work cards (FL-20 spec §5.1) and composes its `cloud`
    block from `FleetCloudService.usageSummary(userId)` (plan §5). The two monies stay separate: FL-20 owns session /
    run model cost, FL-17 owns machine list-price cost, and neither reaches model-spend Budgets (FR-24).
20. **(P2) Needs-a-look items carry one action** (the C §4.6 shape): idle → **Power off…** (`?cloud=power-off`),
    powered off by policy → **Power on…** (`?cloud=power-on`); the computer page opens that confirmation from the
    query. **Keep running** and **Destroy…** are on the page itself. The item id carries the window start, so one
    window is one item.

21. **(P3) Sign-in token hand-off.** The platform's OAuth flow stores a sign-in on the owner's `plugin:<id>` account
    row; nothing passed it to a plugin before. `MachineProviderFacadeService` now reads it
    (`findConnectedProviderAccount`, `@Optional()` `AuthAccountRepository`) and merges it into the per-call settings as
    `oauthAccessToken`; the plugin prefers a saved `apiToken`. `oauthAvailable` is read off the LIVE plugin (its
    env-gated getter) because the manifest must list `oauth` for the registry's index. The platform never refreshes a
    sign-in (no caller of `refreshAccessToken` exists); the plugin implements it for when one does.
22. **(P3) The OAuth plugins callback** (`apps/web/src/app/api/oauth/[providerId]/callback/plugins/route.ts`) accepted
    only the four sign-in enum ids; it now also accepts an id the API's own `GET /api/fleet/providers` lists for the
    signed-in owner with `oauthAvailable` (`machine-provider-sign-in.ts`, a strict slug pattern first). No provider id
    is named in core (the guard spec still passes).
23. **(P3) The settings are `clientId` / `clientSecret`** (admin-only, global, `x-envVar`
    `DIGITALOCEAN_OAUTH_CLIENT_ID` / `_SECRET`) — the names the OAuth service reads — not the `oauthClientId` /
    `oauthClientSecret` the task text used.
24. **(P3) The overlay-VPN key** needs the preset ticked, the operator's install script AND a join command
    (`FLEET_CLOUD_OVERLAY_VPN_JOIN_COMMAND`, absolute path with `{keyFile}`); otherwise `invalid` (field
    `vpnAuthKey`), never quoting the key. Agents and the CLI cannot pass one: a held create stores its payload, and a
    shell history keeps arguments.
25. **(P3) The site tag.** Every new machine carries `ever-works-site:<first 16 hex of sha256(API origin)>`.
    Reconciliation adopts an unclaimed machine ONLY with this deployment's site tag, so a dev and a prod deployment on
    one provider account never adopt (or offer to destroy) each other's machines. Machines created before P3 carry no
    site tag and are only ever repaired, never adopted.
26. **(P3) An unclaimed machine becomes a row** (status `offline`, `unclaimedAt`, a credential nobody holds, idle
    policy `nothing`, priced from the options when the provider names its size): the needs-a-look item needs a node,
    and Destroy then runs the ordinary chain (busy guard, typed name, audit). Adoption and repair are audited
    `node.cloud.create` by `system:cloud-reconcile` (`act: 'adopted-unclaimed'` / `'repaired'`); no new audit action.
    Owners scanned: everyone with a cloud row, plus everyone with a `node.cloud.create` row in the last 35 days (new
    `FleetAuditService.forActionSince`). At most 5 adoptions per provider + owner per pass.
27. **(P3) CLI** `ever-works fleet cloud …` follows FL-16's `virtual.ts`; idle-policy uses `PATCH` (the catalogue's
    route; the CLI client has no `PUT`).

## Questions for the owner

1. **Runtime pin.** The bootstrap installs `ever-works-node@0.2.7` (`FLEET_CLOUD_DEFAULT_RUNTIME_VERSION`) unless
   `EVER_WORKS_NODE_CLOUD_RUNTIME_SPEC` names another. Should a release step bump it, or should it follow the platform's
   own version?
2. **Spec §8b defaults stand:** OAuth client id / secret as admin-scope settings with env fallbacks (P3); the
   overlay-VPN key is create-time only, never stored.
3. **Organization binding (FR-14):** which Organization is the owner "acting in" on the web — is there a workspace
   scope the dialog should send? Today a cloud computer is created personal (`organizationId: null`) unless a caller
   sends one.
4. **Agent at the Auto rung** (spec S9 says Auto answers 409 until `confirm: true`): today every rung is held for
   approval, like FL-16. Keep?
5. **(P2) Agent idle-policy changes are held for approval** (decision 13) although the catalogue class is `plain`.
   Keep, or let an Agent set "tell me" / "nothing" directly and hold only "power off"?
6. **(P2) Where the Cloud computers usage block lives** (decision 19): today on the hub Overview; once FL-20's Usage
   tab ships, should it move there only, or stay on both?
7. **(P2) The idle power-off while the Fleet is stopped** proceeds (it stops spending, R-36's reading for power-off).
   Confirm.
8. **(P3) Keeping an unclaimed machine.** An adopted machine can only be destroyed (R-36 refuses Remove while it
   exists). Should the owner be able to dismiss it ("it is mine, leave it") — which needs a remembered dismissal,
   i.e. a schema change?
9. **(P3) Sign-in refresh.** The platform stores the provider's refresh token but never refreshes; after 30 days the
   owner signs in again. Should a platform-wide refresh job be added (it would serve every OAuth plugin)?
10. **(P3) The OAuth token request** posts a standard form body to `/v1/oauth/token`; the provider documents query
    parameters. Verify against a real application when the operator registers one (the fake API accepts the form).
