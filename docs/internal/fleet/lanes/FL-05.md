## Decisions

1. **One state machine, in contracts** (`mergeFleetSessionEvidence`, `fleet-session-status.types.ts`): the node runs it;
   the platform writes what the node reports (newer `seq` only) and re-checks every shape. Plan §3 "the same function on
   the platform" — the platform does not re-merge, it trusts the newest report of the machine that saw the evidence and
   refuses only what the contract forbids (an ended session, a shell in `needs_you`/`done`).
2. **No sixth column for the card's lines.** The last user line and the last agent line ride `lastEvidence.detail`
   (`userLine`, `agentLine`), carried forward report to report (CONTRACTS rev 14) — the five §4.2 columns stay exactly
   five.
3. **One hook client, not shell scripts.** Plan §3 named `.sh`/`.cmd` scripts calling `curl` with a `node -e` fallback;
   the node binary is always there (it runs the node and its daemon), so the client is ONE Node script
   (`<state>/hooks/hook-client.cjs`) for Linux, macOS and Windows, and the endpoint file is one JSON file
   (`<state>/hook-endpoint.json`). It reads the endpoint file per invocation (U1), posts with the token, spools on any
   failure (U2), always exits 0 within 2 s and never prints (a Claude hook's stdout would become model context).
4. **`PostToolUse` is registered beside the spec's seven Claude hooks**: without it a permission answered in the
   terminal would leave the card in `needs_you` until the turn ended (U5). Mapped to a `working` hook evidence.
5. **Claude Code Agent sessions get no hook overlay**: the Task-run isolation runs them with `disableAllHooks`
   (FL-04 decision 37, never downgraded); their status comes from the process (and, P2, the screen rules). Owner
   question Q1.
6. **Codex: `-c notify=[…]` for owner AND Agent sessions.** Agent sessions run `--ignore-user-config` under an isolated
   `CODEX_HOME`, which would ignore a `notify` written into that home's `config.toml` (plan §6.1); the command-line
   override still applies. Owner sessions: the person's `config.toml` is only READ, to say "Your own Codex notify
   command is not run in this session" (U11). Codex has no prompt hook, so a `agent-turn-complete` is normalised to
   `prompt` + `stop` (the turn it completes is the prompt) so its finish is news.
7. **Interrupt = a driver's Ctrl-C in a running turn** (the session module tells the pipeline what a driver typed —
   facts only, bytes kept nowhere): `done · interrupted`, not news (U15). Claude's `Stop` does not fire on an interrupt.
8. **`session-end` never ends a row**: Claude fires `SessionEnd` on `/clear` too, and the process exit (FL-04's
   `exited`) follows a real end within milliseconds. It clears an open prompt.
9. **Boundary**: a `stop` with no prompt since the last start/resume, or inside the 5 s window after one, is a
   boundary — `done` without the `finished` key, so no unread and no notification (U12, FR-39).
10. **Idle floor folded into FL-04's sweeper** (`sweepStale` → `decayIdle`, every 5 min) instead of a second Trigger task
    (plan §10's `fleet-session-status-sweeper`): same cadence, one task. It decays only sessions whose machine link is
    up — a lost link never changes a state (NFR reliability); the node's own clock is primary.
11. **`stateChangedAt` is nullable** (back-filled by the migration from `lastActivityAt`, else `createdAt`; stamped on
    every state change by both writers) so the migration adds no NOT NULL column to a populated table.
12. **Version gating** (`CLAUDE_HOOK_MIN_VERSION`, `hook-overlay.ts`): an unknown Claude Code version gets every hook;
    a known older one loses the hooks it predates (U10). The table's minimum versions are best knowledge — owner
    question Q2.

### P2 (2026-10-21, PR #2857)

13. **One item per attention key, filed silently.** `InboxService.sessionAttentionRaised` files the Decision (a question
    or a permission) or the notice (blocked, failed) once per key and never rings the Inbox bell: the session pipeline
    sends its own notification (`fleet_session_needs_you|finished|failed`, deduplicated by the key), so one edge rings
    once (FR-25). The key lives in `sourceMeta.attentionKey`; the lookup reads the user's newest 200 `fleet-session`
    items (no index on JSON).
14. **The Inbox reply types into the session.** A `fleet-session` question/approval reply goes through the
    `FLEET_SESSION_ANSWER_ROUTER` port (leaf file in `inbox/`, bound by the API's global sessions module to
    `FleetSessionService.answer`, resolved lazily through `ModuleRef` — the session service reaches the Inbox through
    the attention delivery, so a constructor dependency back would be a provider cycle). A refusal re-opens the item
    (the reply's own claim/release). The free text is never stored on the item.
15. **The platform never sends keys.** `session.answer { key, answer: { optionId } | { text } }`; the node maps the
    option to keys (`answer-typist.ts`: Claude Code digits, Esc for deny; a rule's own keys; a question's "other" entry
    - text + Enter) and refuses a key that is not its current attention (`invalid` → "Already answered in the
      terminal"). After an answer the node reports `answered` (source `structured`, above the rules), and the screen rules
      leave the session alone for 5 s while the CLI redraws.
16. **Ending a session**: an open question/permission expires (the Inbox item is ARCHIVED — never answered, R-12); a
    session that ends `failure` raises a `failed` attention (`fleet-session:<id>:failed:exit`, "exit code N") — the Inbox
    notice and the "failed" notification (U14). FL-04's end paths call `FleetSessionStateService.sessionEnded`.
17. **"Stale after 24 h"** (R-12, FR-27a) is NOT built yet: the Inbox has no stale state. A follow-up (P3 or the
    stabilisation lane) can mark it from the sweeper. Recorded under Next step.
18. **Rules ship as TypeScript data** (`apps/node/src/core/sessions/rules/session-rules.ts`) — not `.json` files — so the
    node bundle needs no asset copy; the guard still validates them at start (FR-36) and names the rule id. Rules run
    every 2 s only for a session with no hook in 10 s, not answered in 5 s, and either moving (output in the last
    minute) or waiting.
19. **R-32 setting**: read from `agents.permissions.canAnswerOtherSessions` (absent = off). There is no editor yet, so
    an Agent answers only its OWN session's questions. Owner question Q4.
20. **Toast suppression while the detail is open** (FR-39) is not built: the detail acknowledges on open (unread
    clears), but the bell's toast is not suppressed per session. Follow-up.

### P3 (2026-10-21, PR #2863)

21. **The board is one read** (`GET /sessions?view=board`, the FL-04 list route with a `view` parameter — CONTRACTS
    §11.2 keeps one path): live sessions only, grouped by `fleetSessionBoardColumn` (contracts — the same rule the web
    and the palette use), sorted in code after the query (Postgres and SQLite order NULLs differently). The list mode
    reads the existing paged list (200) and groups by day / week and by who on the client.
22. **The Activity page stays the single URL writer**: the board reports its state as a query string
    (`onStateChange`), as the Live Feed does; `?view=sessions` with the flag off falls back to the Log (T-36), and the
    tab and the `n` key are absent.
23. **Polling, not the relay bus**: the board re-reads every 4 s while visible (FR-43's 5 s); a card that changed column
    moves with a view transition where the browser has one, and the move is announced in a polite live region. The
    relay-bus `fleet.session.changed` event of plan §3 is not emitted yet (follow-up).
24. **Fleet → Sessions** (`SessionsByComputer`) is registered on the server (`modules/fl-05-sessions.server.ts`) into
    FL-01's hub slot; it groups the board's live sessions by computer and shows every computer, with its online state,
    consents and "Agents need work switched on here". The computer page's Sessions tab stays FL-04's (the same cards,
    now completed) — "this view filtered to one Node" in substance; not re-implemented.
25. **Palette**: the empty query opens with **Needs you** (newest wait first, at most 6 — the palette's own
    Ctrl/Cmd+1…6) and **Recent sessions** (done, then idle), from one board read each time the palette opens while the
    hub is on. Sections reuse the existing `suggested` / `recent` kinds (no new union member).

## Questions for the owner

- **Q1 — status hooks for Claude Code Agent sessions.** Agent sessions run with `disableAllHooks` (FL-04's isolation).
  Allowing ONLY the node's own status hook (an allow-list of one command) would give them exact status; built: no hooks,
  status from the process / screen.
- **Q2 — hook minimum versions.** `CLAUDE_HOOK_MIN_VERSION` (`PermissionRequest` 2.0.45, `SessionEnd` 1.0.85,
  `SessionStart` 1.0.62, `UserPromptSubmit` 1.0.54, the rest 1.0.38) is best knowledge; confirm or correct.
- **Q3 — rules-file updates** (spec §8b): built the default — rules ship inside the node package only (P2).
- **Q4 — "may answer other sessions" (R-32).** Read from the Agent's `permissions.canAnswerOtherSessions`; no editor
  exists, so it is off for every Agent. Where should the switch live (the Agent's Permissions panel)?
- **Q5 — Claude Code key map.** Digits choose an option in Claude Code's dialogs and Esc denies; a question's free text
  goes through its "other" entry (`<n+1>` + text + Enter). Built from the CLI's documented behaviour, not yet watched on
  a real session — confirm on a machine before relying on answers from the card.
