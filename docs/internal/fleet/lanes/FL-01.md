## Decisions

- **13 families, not 11.** CONTRACTS §2.1 lists `view · sessions · desktop · logs · services · docker ·
processes · ports · files · commands · schedules · checkouts · machines`; the epic text's eleven
  predates revision 2. The `machines` family is labelled "Lifecycle" in the UI (spec §5.10 as audited).
- **Audit name `node.policy.change`** (CONTRACTS §7), one row per family whose audience changed,
  details `{ family, from, to, requestedBy, confirmationClass: 'plain', outcome: 'success' }`.
- **Legacy `controlPolicy` stays the `desktop` mirror** (CONTRACTS §2.1): reads take the map's
  `desktop` entry first and the column second; every write that touches `desktop` writes the column
  in the same `UPDATE`. No data backfill is needed — read-through covers every existing row, and
  nothing but this epic writes either column today (`rg controlPolicy` at the base commit finds only
  readers).
- **Registry names are CONTRACTS §11.1's**: `registerComputerTab`, `registerOverviewBlock`,
  `registerHubTab` (the plan's `registerHubPanel` / `registerOverviewSlot` are not used).
- **`GET /api/fleet/nodes` keeps its owner-only answer by default**; the hub asks
  `GET /api/fleet/nodes?scope=visible`, which adds Organization-bound nodes whose `view` audience
  includes the caller and stamps `viewerRole` on every row. Settings → Fleet, the runner pill, the
  panic controls and the lease path are therefore byte-for-byte unchanged (FR-15).
- **Organisation roles** come from the Organization the node is bound to: the Tenant owner of that
  Organization → `org-admin` (`OrganizationMember` role `owner` is synthesised, there is no roster
  row); a roster row `admin` → `org-admin`; `member` → `org-member`; anything else → `stranger`.
  Tenant membership without a roster row is **not** enough (fail-closed; see questions).
- **"Needs a look" items are exactly CONTRACTS §4.6** (revision 4: thirteen kinds, with
  `session-unconfirmed` and `service-failed`); the sanitiser drops any extra field a producer adds, and the web resolves the
  computer's name from `nodeId` against the node list it already holds. The HTTP answer is
  `NeedsALookItem[]`; a skipped (failed or timed-out) producer sets the response header
  `X-Fleet-Partial: true` (plan §5) and is logged with its id.
- **`DELETE /api/fleet/nodes/:id` keeps working without a body** (CONTRACTS rev. 3 / Constitution X):
  `confirmName` is optional and checked only when sent; the hub always sends it.
- **FL-01 creates every hub route file and `ROUTES` constant of CONTRACTS §11.1** (each renders the
  honest "arrives with FL-nn" state until its epic registers a tab).
- **Roster facts are read by table name** (`FleetOrganizationDirectory`): importing the
  `OrganizationMember` entity into the agent `FleetModule` pulled the whole user / work / zod entity
  graph into every consumer and ran `apps/api/src/fleet/fleet.module.spec.ts` out of memory (4 GB heap;
  it passes on the base commit and again after the change). The table-name lookup goes through
  TypeORM's registered metadata, so identifiers are still escaped per driver; an integration spec on a
  real better-sqlite3 schema proves it.
- **A shared row is an allow-list** (`FLEET_SHARED_VIEW_FIELDS` in `fleet.service.ts`, pinned by an
  exact-keys test): identity, kind, state, OS, versions, capabilities, last check, disk free, worker
  state, which CLI is throttled until when (not the node's sentence about it), the policy, nesting, and
  `viewerRole`. Withheld: control holder, cost and limit ceilings, recording settings, pending rotation,
  housekeeping, the CLI's signed-in account, free-text reasons; `enrolling` rows are never shared. A row
  still marked online whose heartbeat is older than the offline window is shown offline (the sweep only
  runs on the owner's reads; nothing is written). The node detail answers anyone in `view`; its job
  history stays the owner's. Adding a field to the shared view is a decision, not a side effect.
- **No compare-and-set on the policy write**: two concurrent owner edits of the same node's map are
  last-write-wins (as spec U12 accepts for the favourite). The `desktop` mirror is still never
  half-written — both columns go in one `UPDATE`, asserted.
- **Seams for the siblings**: FL-02's link authoriser calls `FleetAccessService.assertFamily(node,
caller, family)` (exported from `@ever-works/agent/fleet`); its `FLEET_LINK_ACTION_FAMILIES` list
  equals `FLEET_ACTION_FAMILIES` here and can alias it. FL-03 registers producers with
  `NeedsALookService.register(producer)` (or the `NEEDS_A_LOOK_PRODUCERS` token) and its web tabs and
  blocks with `registerComputerTab` / `registerOverviewBlock`. `readNodeConsents` in
  `components/fleet/fleet-consents.shared.ts` reads FL-02's `consents` once it is on the view.

## Questions for the owner

1. **Nothing binds a node to an Organization today.** `fleet_nodes.organizationId` exists, but
   `POST /api/fleet/nodes/enrollment-token` does not accept it and no other path writes it, so every
   node is unbound and every non-owner derives `stranger`. FL-01 derives the roles and the families
   as specified; a "Share with an Organization" control on the computer's Settings tab is the
   smallest follow-up that makes S9/S10 reachable. Not built here (not in the epic).
2. **Tenant members without a roster row.** Organization access elsewhere is tenant-wide
   (`OrganizationMembershipService.ensureMember`). For a machine I chose the stricter reading: only
   the Tenant owner and roster members derive a role. Confirm, or widen to "same Tenant →
   `org-member`".
3. **Default `view: org-members`** for a node bound to an Organization (spec §8b, CONTRACTS §2.1):
   implemented as the default; it grants listing only.
4. **Capability tags, the cost ceiling and resource limits stay owner-only.** The act table puts
   rename, pause, drain and remove in `machines`; these three are not in it. Should an org admin the
   Lifecycle family admits also change them? Default: owner only.

### PR 3 — roles in use (`feat/fl-01-fleet-hub-p2`)

Decisions made while building it:

- **`machines` gating is resolved once, before any write**, by `FleetService.resolveMachinesActor`
  (404 outside `view`, `permission_denied` naming Lifecycle outside the family). The owner acts
  exactly as before — same service calls, same arguments, same audit rows. A role the family admits
  acts on the OWNER's registry row (`ownerUserId`, so the existing owner-scoped service methods and the
  drain's claim release are reused untouched) and is recorded as the actor, with
  `{ family: 'machines', viewerRole, requestedBy }` in the audit details. It is answered with the view
  the owner shares (`getVisibleForUser`), never the owner's full row.
- **A mixed PATCH from a non-owner is refused before any write** when it carries an owner-only field
  (capabilities, cost ceiling, favourite, policy) beside a lifecycle field, so it can never half-apply.
  Capability tags, the cost ceiling and the limits stay owner-only (not in the act table; owner
  question A19).
- **`confirmName` on remove is read by name (`@Body('confirmName')`), not through a DTO**, so a body
  the route never validated keeps being accepted exactly as before; it is checked only when sent and
  only after the node resolved (a wrong name never tells anyone a node exists). A matching name adds
  `confirmationClass: 'confirm-destructive'` to the `node.delete` row; owner rows without it are
  byte-identical to before. Merged with FL-02's `closeLink` on remove (both paths close the link).
- **An `enrolling` row is the owner's alone** in `FleetAccessService.resolveForFamily` too (it already
  was in `listSharedWith`), so an outstanding one-time token can never be opened or acted on by a role.
- **AW-11 take-over reads the `desktop` family through `effectiveControlPolicy`** and the caller's
  role through `FleetAccessService.roleFor` (appended, `@Optional()`; without it the arbiter is the
  owner-or-stranger check it always was). `viewerRoleForNode` stays exported, marked deprecated.
  The API module spec now pins that the arbiter gets the access service.
- **The ⋯ menu mirrors the server, it never decides**: lifecycle acts disabled with the reason beside
  them ("Ask the owner of build-01 to allow org members: lifecycle."), the star owner-only, Copy link
  always. Drain counts the jobs in flight from the owner's own node list when the dialog opens; a
  count it cannot know is said as such, never as "no jobs". Pause on a drained computer is refused in
  the menu ("Return it to the fleet first"), because the existing pause write would lift the disable.
- **The Settings tab mounts the Computers tab's node panel unchanged** (`FleetNodeDrawer`: capability
  tags, limits, cost ceiling, lifecycle, credential) behind "Open machine settings", owner only, wired to
  the same server actions; a rotated credential's one-time token is handed over at once with
  `FleetEnrollHandoff`. The tab is rendered through a small server wrapper (`SettingsTabServer`) that
  reads the public API base and downloads, exactly as the Computers tab does.
- **Organisation roles cannot be walked in a browser yet** (nothing binds a computer to an
  Organization, A17): `flow-fleet-roles-contract.spec.ts` covers the stranger, the policy audit and
  the typed name over HTTP; the role derivation and `machines` gating are pinned in the API and agent
  specs.
