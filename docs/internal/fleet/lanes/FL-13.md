## Decisions

1. **A new contracts file, `fleet-schedules.types.ts`,** holds the cadence, the clock, the `schedule` family's
   messages and the views (plan §4.3 put the link messages in `fleet-commands.types.ts`; one file per family
   keeps FL-12's file as it merged). `FleetCommandRunView` gains only the optional `scheduledFor`.
2. **One clock for three consumers.** `nextFleetScheduleFire` / `previousFleetScheduleFire` /
   `fleetScheduleCatchUp` are pure (`Intl.DateTimeFormat` only) and shared by the API, the node and the web. A
   wall time a spring-forward day skips fires as far past the jump as it was scheduled before it (02:30 → 03:30);
   a repeated fall-back time fires once, at the first of the two; "every N minutes" is the cron `*/N` of the
   minute field (it restarts every hour). A computer that never reported a zone runs on UTC.
3. **Name length 120** (CONTRACTS §10 wins over the spec's 80).
4. **`pausedReason` values are CONTRACTS §4.4's** `user · failures · breaker` (plan §4.1 said `failure-streak`).
5. **A command line that trips the secret scanner is refused (`invalid`, with a way out).** FL-12 stores a redacted
   copy and sends the real line once; a schedule's line must be STORED to be re-synced on every link open, and the
   platform never stores a secret. The hint says to keep the secret in a file or environment variable on the machine.
6. **A Command schedule shows in every workspace scope.** It is its author's and its computer's (`fleet_commands` has no
   Organization column), like the person's Commands; the `node_schedule` collector reads the caller's own schedules.
7. **The reconcile pass runs in the API on every install** (`FleetScheduleReconcileCronService`, `*/5 * * * *`, under
   `DistributedTaskLockService`), Trigger.dev or not: the node link lives in the API process, so a job-runtime task
   (plan §10 `fleet-schedule-reconciler.task.ts`) could only call back into it. Not written.
8. **One short-lived `schedule` channel per request** (sync, runs, runNow) opened as `system` for the platform's own
   sync/reconcile and as the person for Run now — it works from any API replica through the relay bus, like FL-12's
   cancel. The kill switch refuses every channel open (FL-02's authoriser), so nothing syncs while it is on; the node's
   own loop stops on `link.pause`.
9. **A schedule's run keeps the machine's run id as its row id**, so reconciling twice is one row; a Run now's run id is
   minted by the platform and passed in `schedule.runNow`. Reports carry `trigger` (`timer · catch-up · run-now`).
10. **Generations.** Every write stamps the changed row with `max(syncGeneration of the computer's rows) + 1` and re-sends
    the computer's whole set with that generation; the machine's answer marks every row of the set `syncedGeneration`.
    `pending` = `syncGeneration > syncedGeneration`. A refusal of one definition (folder outside the allowed roots) and
    "this node is older than schedules" are kept in memory per replica (no column for them in §4.4).
11. **The node's loop**: one timer armed to the earliest next fire (at most 60 s ahead, so a sleep or a clock change is
    noticed); on every tick, per schedule, `fleetScheduleCatchUp(since = max(armedAt, lastFireAt))` → run once
    (within 2 min = `timer`, later = `catch-up`) or one `skipped-offline`. `armedAt` resets when the cadence changes, so a
    new or edited schedule never catches up a fire from before it. A run a previous process left `running` ends
    `failed (node-restart)` when the node starts (FL-12's decision 12 follow-up, for schedules).
12. **Kill switch remembered across restarts** (spec §8b default): the node persists the last `link.pause` / `link.resume`
    in `<configDir>/schedules/_state.json`; a remembered pause ends when a ready link has said nothing for 5 s (the
    platform re-sends a pause in force right after `link.ready`).
13. **Run now / Pause / Resume** go through `ScheduleControlService` (one control path for every source) via the
    `NODE_SCHEDULE_PORT` token the API's global `FleetSchedulesApiModule` binds to `FleetScheduleService`; `run-now`
    gains an optional `{ confirm }` body (FR-25). The Activity row menu asks with `window.confirm` before it sends it.
14. **Edit confirmation**: a move or a change of the command or the folder asks for `confirm`; a rename or a new cadence
    does not (FR-25 names create, run now, move, delete; changing what runs is treated like creating it).
15. **"Open full output" for a schedule's run** reuses FL-12's route and `command.read`: the node's command module asks
    the schedule history (`findStore`) when its own store does not hold the run.
16. **The computer tab lists through the Schedules view** (`GET /api/schedules/page?sourceType=node_schedule&node=<id>`,
    via the BFF route `/api/fleet/nodes/:id/schedules`); each row carries the full `nodeSchedule` facts (workspace reads
    only — the flat list keeps its thirteen keys).
17. **`HomeScheduleKind` gains `node_schedule`** (Home's Today panel maps every source with a `switch` that has no
    default); its contract test's count moves from 7 to 8.

### P2 (2026-10-21)

18. **Agent writes are held for approval.** `fleet_schedules_create|update|delete|run` file an Agent Action Approval
    Queue proposal (`payload.kind: 'fleet-schedule-write'`); `FleetScheduleProposalListener` applies exactly it, as the
    Agent, once a PERSON approves (FL-12 decision 15's posture: a schedule runs commands in the owner's shell, again and
    again). Pause and resume apply at once. The tools see only `requestedBy: 'agent'` schedules.
19. **An Agent-session schedule is marked by labels** on its recurring Task — `fleet:session-schedule`,
    `fleet:provider:<cli>`, `fleet:checkout:<uuid>` — copied to every instance by the recurrence clone. R-29 rules out a
    per-Task node column; the computer is always the Agent's affinity at fire time.
20. **Each fire is an FL-04 Agent session**, started from the one dispatch choke point
    (`TaskTransitionService.dispatchAgentRun`, after its ownership check) through `TASK_SESSION_SCHEDULE_DISPATCHER`
    (bound by the API to `FleetSessionScheduleDispatcher` → `FleetSessionService.start`, kind `agent`, `taskId` = the
    instance). No second scheduler; review runs are never redirected.
21. **A fire that cannot start** (not pinned any more, offline, no `--work`, kill switch) answers the dispatch's failure
    shape (`error: 'session-<code>'`); the 60-minute "wait while offline" of spec U10 and the missed-fire sweeper (T-33)
    are not built — question Q4.
22. **The schedule routes FL-19's catalogue named** (`/api/fleet/schedules…`) are built as the resource surface beside
    P1's paths; the nine catalogue rows are `live` and the MCP whitelist carries them.
23. **The breaker** is fleet-side (`/nodes/:id/schedules/pause-all` + `resume-all`): AW-10's `disable-all` does not exist
    yet, so its scope `node` is this route; one `pausedAt` instant is the Undo key. It pauses Command schedules only;
    pausing the computer's Agent-session schedules (recurring Tasks) with it is a follow-up.
24. **The computer chip** on recurring Tasks comes from affinity in the active Organization (`SchedulesService`
    `attachComputerChips`); the computer tab now lists every source on the computer (`/schedules/page?node=`), so
    pinned recurring Tasks appear under "Agent sessions" with Run now / Pause / Resume.

### P3 (2026-10-21)

25. **The OS-scheduler fallback is one file** (`apps/node/src/core/link/modules/schedule/native-scheduler.ts`): the
    crontab block between markers (Linux), one LaunchAgent per schedule (macOS), the Task Scheduler folder
    `\EverWorks\` (Windows). A cadence the OS cannot express (an arbitrary cron on macOS / Windows) is skipped with the
    reason; "every N minutes" on launchd is a plain `StartInterval` (not aligned to :00).
26. **Opt-in: `start --native-schedules`** (plan §6 reads "only when the node is not a service"): nothing edits a
    person's crontab, LaunchAgents or Task Scheduler unless asked. It installs only when the process does not run under
    a service manager (`INVOCATION_ID` from systemd, or `EVER_WORKS_NODE_SERVICE=1`), re-installs on every change of the
    held set (deduplicated), and `unenroll` removes everything it wrote.
27. **No double runs:** the loop writes a lease (`<configDir>/schedules/_alive.json`, pid + time) on every tick; the
    hidden `ever-works-node schedule-run <id>` does nothing while a live node process holds a fresh lease, else it loads
    the held set, runs whatever is due with the loop's own catch-up rule, waits for the runs and exits.

## Questions for the owner

- **Q1 — secrets in a schedule's command line.** Built: refused (decision 5). Alternative: keep the real line only on
  the machine (the platform would hold a redacted copy and could never re-sync it after the machine loses its cache).
- **Q2 — a schedule's scope.** Built: the author's own schedules show in every workspace scope (decision 6). If they
  should follow the computer's Organization instead, the collector can filter on the node's `organizationId`.
- **Q4 — an Agent-session fire while the computer is offline.** Built: the fire fails at once with the reason
  (decision 21). Spec U10 wants it to wait up to 60 minutes; that needs the session start to queue (FL-04 refuses an
  offline computer) or a sweeper (T-33).
- **Q5 — cost on Agent-session rows (T-35).** Each fire is a Run with its cost on the Runs ledger; the row's "last 30
  days" total waits for FL-20's roll-up.
- **Q6 — the Windows service sets `EVER_WORKS_NODE_SERVICE=1`?** The fallback treats a process as a service when
  systemd's `INVOCATION_ID` or `EVER_WORKS_NODE_SERVICE=1` is set; the Windows install script does not set the latter
  yet, so `--native-schedules` under the Windows service would also register Task Scheduler entries (harmless — the
  lease makes them no-ops — but redundant).
- **Q3 — shared viewers and the time zone.** `timeZone` is on the owner's node view only; `toSharedView` is a pinned
  allow-list, so an Organization member scheduling on someone else's computer sees its times in UTC until it is added.
