## Decisions

1. **The node keys a checkout by its absolute PATH; the platform row is unique on `(nodeId, path)` and carries its own
   uuid.** Every platform→node request names the path, and the node acts only on a path its own registry (or its Task
   pool) holds — never on a folder the platform made up. Plan §4.3's `checkoutIds` param is therefore `paths`
   (`FleetCheckoutsListParams.paths`); CONTRACTS revision 8 records it.
2. **`checkouts.list` needs `work-or-manage`** (a `FLEET_LINK_VERB_CONSENT_OVERRIDES` entry, spec U2: a `--work`-only
   node still lists its Task worktrees). Discovery (`rescan`) needs `--manage`, checked on the machine and narrowed by
   the platform. A `--work`-only node's reply is never `complete` (its registry is not reported), so the platform never
   marks discovered rows `missing` from it.
3. **A plain list is a read under `view`, not refused by the kill switch.** The rows and their age stay visible while
   all computers are stopped; rescan, refresh, fetch, archive and restore are refused `kill_switch` (the platform),
   and the node refuses every state-changing verb while the link is paused and cancels a fetch in flight. Spec U3 says "every link request" — this keeps reads visible (owner question Q1).
4. **Code folders and the last scan time travel only in the list reply** (plan §4.3) and are kept per API process
   (`FleetCheckoutService.lists`), not stored: CONTRACTS §4.3 has no column for them. An API restart shows "Scan
   build-01 to see the folders it lists" until the next list. Busy and reaper notes are kept the same way.
5. **`node.checkout.sync` also records a person's rescan** (`op: 'rescan'`): CONTRACTS §7 has no `scan` name and a
   rescan is a state-changing request to the machine.
6. **Task worktrees are read live from the pool** (`scanWorkspaceRoot`, offline) and never written to the node
   registry; fetch on one is refused `invalid` ("kept in sync by their runs") — the pool's per-repository lock is not
   this module's to take.
7. **Reaper rules 5–6 were NOT extracted into a shared `checkout-evidence.ts` in P1** (T-09): the reaper is fail-closed
   and untested here; moving its code without running its suite is the riskier change. P2's delete changes-check
   computes the same evidence (uncommitted, commits unreachable from any remote ref) in its own module; the reaper keeps
   its own code. T-09 stays open as an owner-visible note.
8. **Slow operations are folded in through `FleetOperationsService.onEnded`** (an additive hook on FL-02's service,
   fired once on the replica that ended the operation): a `checkouts.list` that ran past the 2-second inline window and
   a fetch both carry their result in `operation.done`, and the sync result names its path, so no in-memory
   operation→row map is needed across replicas.
9. **The link open triggers a list** (`FleetCheckoutLinkListener`, spec FR-11 "on link open"); the ten-minute
   reconcile asks connected nodes not heard from for ten minutes, and sweeps `creating` rows older than ten minutes to
   `missing` (compare-and-set on `updatedAt`).
10. **Work matching reads `Work.sourceRepository`** (`url`, else `owner`/`repo` on github.com, plus a GitHub App
    installation's `repoFullName`), host-aware, oldest Work first. The Work's own data/website repositories are not
    matched yet (follow-up). Only the Node's owner sees the linked Work's NAME; others see that a Work is linked.
11. **Migration FKs follow plan §4.2 exactly**: `nodeId` CASCADE, `parentCheckoutId` and `workId` SET NULL (no `userId`
    FK — a user's nodes already cascade). `fleet_sessions.checkoutId` keeps no FK (a session row outlives its
    checkout).
