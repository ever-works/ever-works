## Decisions

1. **Live output by polling the run rows, not a viewer socket (P1).** FL-02's viewer gateway bridges one browser
   socket to one NODE channel; a Command's output is on channels the platform itself holds (one per run, on the API
   replica that took the request). A browser on another replica would need a cross-replica fan-out the relay bus does
   not offer yet. P1 therefore keeps a head/tail buffer per run in the service, flushes it to `fleet_command_runs`
   at most once a second while the run is live, and the hub card and the CLI read `GET /api/fleet/commands/:id`
   every second while anything runs. Every replica reads the same rows, so it is correct behind several replicas
   without new plumbing. The attach-token route and `/ws/fleet/command/:id` of plan §5 are not built; question Q1.
2. **The node's `command.output` is authoritative.** Just before `EXIT` the node sends the head and tail it kept
   (64 KiB each), the byte count, whether it capped at 10 MiB and, when it ended the run itself, why (`timeout`,
   `kill-switch`, `drain`, `shell-failed`, `cancelled-by-user`). The platform's live copy may have missed bytes while
   the link was down; the node's never did. CONTRACTS §3.3 names `command.output` as "head/tail on finish"; the fields
   are written down in revision 11.
3. **Refusals per computer live on the run row.** A computer that refused before the command ran (`unreachable`,
   `consent_missing`, `permission_denied`, `unsupported_on_node`, `kill_switch`) gets a run `failed` with
   `failedReason` null and the CONTRACTS §8 error in two new columns `errorCode` / `errorHint`; the CONTRACTS §4.4
   `failedReason` enum is not widened. `outputBytes` and `capped` are new columns too (spec U6's "Output capped at
   10 MiB"). All four are in FL-12's own slot `1796120100000` and written into CONTRACTS revision 11.
4. **The channel opens with `{ commandId, nodeId, runId }`** — CONTRACTS §3.3's two fields plus the run id, so the
   node keys its output file by the platform's run id.
5. **No new capability tag.** `commands` is not advertised: the heartbeat caps tags at 16 by default and a node
   older than this epic already refuses the `command` family `unsupported_on_node` (spec §6 compatibility); that
   refusal lands on the run's card as "update the node on build-01 to run commands".
6. **The folder rule is the owner sessions' rule** (FL-04 decision 10): the home folder or a folder the machine's
   owner allowed (`sessionExtraRoots`), canonicalised, symlinks resolved, case-insensitive on Windows. R-39's shared
   `allowed-roots.ts` does not exist yet; when FL-08/11/14 lands it, the command module switches to it.
7. **The shell is FL-04's login shell** (`resolveLoginShell`): `$SHELL -l -c <command>` (`/bin/zsh` on macOS,
   `/bin/sh` elsewhere when `$SHELL` is unset), on Windows `pwsh` when it is on PATH else Windows PowerShell, with
   `-NoLogo -NonInteractive -Command`. The environment is the scrubbed `buildNodeCheckEnv()` allow-list (never
   `FLEET_*`, `EVER_WORKS_*`), stdin is `ignore`.
8. **Agent-requested Commands** (P2) write `requestedBy: 'agent'` on the row and `agent:<id>` in every audit row
   (CONTRACTS §2.3); the row has no Agent column (§4.4 has none).

### P2 (2026-10-21, PR #2846)

14. **"Open full output" is a streamed download, not an FL-02 operation.** `GET /api/fleet/commands/:id/runs/:runId/output`
    opens a short-lived `command` channel (`stateChanging: false`), sends `command.read { runId }`, and pipes the
    machine's `DATA` frames into a `text/plain` attachment (`nosniff`, file name from the computer's stored name and the
    run id, never the request) until `END`. Before the first byte a refusal is the CONTRACTS §8 envelope (`unreachable`
    names when the computer was last seen; `not_found` when it no longer keeps the file). The full output is the
    person's own and is NOT passed through the secret scanner (it is never stored on the platform); the stored head
    and tail still are.
15. **An Agent never runs a command by itself.** `fleet_commands_run` always files an Agent Action Approval Queue
    proposal (`payload.kind: 'fleet-command-run'`, `humanDecisionRequired`, no subject key — the same command may
    rightly be asked for again); `FleetCommandProposalListener` runs exactly it as the Agent once a PERSON approves.
    Without the queue the tool refuses. The AW-24 classification is `machine.run` for the run and the cancel,
    `read.internal` for the reads. Question Q2.
16. **The Agent reads see only Agent-requested Commands** (`requestedBy: 'agent'` of the owner); a Command a person
    ran is as unknown to the tools as a missing one. There is no Agent column (CONTRACTS §4.4), so one owner's Agents
    see each other's commands. Question Q3.
17. **"Last command" route** `GET /api/fleet/nodes/:id/commands/last` (CONTRACTS §11.2 addition): the caller's own
    latest run on that computer (spec §8b default), behind the `commands` audience (a viewer outside it reads
    `{ last: null }`).

### P3 (2026-10-21)

18. **Folder picker = the picked computers' ready checkouts (FL-14) under the folder field** (a `datalist`, at most
    five computers read at once, paths de-duplicated); the field still takes any path and the node still decides
    (home or an allowed folder). Shown only while `FLEET_CHECKOUTS_ENABLED` is on.
19. **Re-run from Recent** fills the composer from the stored Command (computers that can still take it, folder,
    timeout snapped to the menu) and opens the platform's confirmation; it is the same request a person would type.
    A command line stored REDACTED is not re-run (it would run the placeholder) — the person types it again.
20. **Retention** of stored heads and tails: `FleetJobRetentionService.purgeExpiredCommandOutputs` (03:45 UTC, the
    job-body pass's switch `FLEET_JOB_PURGE_ENABLED` and window `FLEET_JOB_RETENTION_DAYS`, default 30) NULLs
    `outputHead` / `outputTail` of ended runs older than the window and keeps the rows.
21. **"A Command with a cadence hands over to FL-13"** stays as P1 built it: `cadence` is refused `invalid` on the
    one-off route; FL-13 owns the Schedule route and its validation, on the same `fleet_commands` table.

## Questions for the owner

- **Q1 — a viewer socket for Commands.** Live output is polled once a second (decision 1). A socket per Command
  needs the API replica that holds the run channels to publish output on the relay bus for a browser on another
  replica. Built: polling; the socket is a follow-up if one second is not live enough.

9. **One `node.command.run` row per computer, written when it is dispatched or refused** — spec FR-12's "within 2
   seconds" cannot wait for a ten-minute command's end, and "who ran what" must exist even if the platform dies
   mid-run. The end (exit code, duration, truncation) is on the run row; a stop the machine made for the kill switch
   or a drain writes `node.command.cancel` (`requestedBy: system:kill-switch|drain`), a person's stop writes it at the
   request (`reason: user`).
10. **Order of a run request:** shape → every computer's existence and `commands` audience (an unknown or invisible
    id is the 404 of the whole request; a visible one outside the audience is that computer's `permission_denied`)
    → kill switch → eight running / ten a minute → the confirmation (`confirmation_required` with one line per
    computer) → rows → background dispatch. The ten-a-minute window is per API replica (in memory).
11. **Cancel opens a short-lived channel of its own** with the run's `{ commandId, nodeId, runId }` and
    `stateChanging: false` (stopping only stops spending); the node finds the run by id, so it works from any API
    replica. It is in P1 (route + service + node + the hub's Stop button); P2 adds the Agent tool.
12. **A node restart is not told apart from a lost link yet**: both end the run `failed (link-lost)` once the
    channel's resume window passes (the full output stays on the machine). `node-restart` needs the node to report
    unfinished runs after it starts again — a follow-up.
13. **The CLI joins FL-04's `fleet` group** (`fleet session …` landed first): `fleet commands run` (alias
    `fleet command run`) is added to the same `fleetCommand`.

- **Q2 — may an Agent run a command without asking?** Built: every Agent command waits for a person's approval in
  My Decisions, whatever the `machine.run` rung says. If the rung `auto` should let an Agent run commands directly,
  the tool can check the resolved ladder entry and skip the proposal.
- **Q3 — Agent command visibility.** Agents of one owner see each other's commands (no Agent column on
  `fleet_commands`). A column `requestedByAgentId` (a new migration slot) would scope each Agent to its own.
