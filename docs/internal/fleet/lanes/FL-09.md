## Decisions

1. **Node module files follow CONTRACTS R-40, helpers in one folder.** The module entries are
   `apps/node/src/core/link/modules/services.ts` and `processes.ts` (one entry each in `modules/index.ts`'s
   `NODE_LINK_MODULES`); their building blocks (root runner, blast radius, argv safety, per-OS managers, `ps`
   parsers, GPU stats, self-protection) live in `modules/machine-facts/`. The plan's `modules/{services,processes}/`
   folders were written before R-40.
2. **A machine-facts child never uses a shell** — `machine-facts/exec.ts` runs `execFile` with `shell: false` on
   every OS (the node's general runner uses a shell on Windows), a scrubbed environment (`LC_ALL=C`; PATH, home,
   the systemd user bus, the Docker context; never a credential) and a deadline + output cap. Windows work goes
   through `powershell -EncodedCommand`, with names as single-quoted literals of already-validated text.
3. **The node computes the blast radius, the platform only carries the acknowledgement.** The platform checks the
   base class (`confirm` / `confirmName`) after the link's gate; it forwards `acknowledgeBlastRadius`, and the node
   — which alone knows what a service carries — refuses an unacknowledged blast radius with
   `confirmation_required` and its sentence. List rows already carry the class and the warning, so the dialog
   opens before the first call; the server's answer is still what decides.
4. **The link's gate runs BEFORE the confirmation.** `FleetLinkService.authorizeRequest` (new, additive) is the
   `request` gate without contacting the machine; a caller who may not act therefore never learns the act's
   summary or the machine's name from a `confirmation_required`.
5. **Audit: one row per act, prompts and `not_found` excluded.** `confirmation_required` is the protocol asking,
   not an act; a refusal to a caller who may not see the machine is not recorded against it. Every other refusal
   is `outcome: refused` (`failed` for `operation_failed` / `internal`) with the code; the owner sees refused rows
   (the port's `describe` puts the node owner on them).
6. **The root rule is `sudo -n --` (Unix) or an admin probe (Windows), cached 60 s per command.** A refusal is
   `root_required` whose hint IS the exact command (`sudo systemctl restart nginx`, `Restart-Service -Name W3SVC`)
   and whose details carry `{ command, shell, machine }`. `-S` is never passed; no password field exists.
7. **The node's own service and process tree are untouchable from here.** A service whose main pid is the node or
   one of its ancestors, or whose name matches the node's unit / launchd label / Windows service, has no acts;
   `processes.signal` refuses the node, its ancestors, its session daemon (matched on the `session-daemon` verb,
   conservatively) and PID 1 with `invalid`. The node's CHILDREN are not protected.
8. **Docker is a blast radius only when containers are computers (FL-16).** The spec says so explicitly; the
   table has the rule behind `hostsChildNodes`, off until FL-16 wires it.
9. **Agent acts: calling the tool satisfies `confirm`; a blast radius and every SIGKILL are held.** Held acts reuse
   the existing owner-approval seam (`sources.proposals`: `actionType 'other'`, platform-written
   `payload.kind: 'fleet-machine-action'`, human decision required) and run through
   `FleetMachineProposalListener` only on a person's approval, re-validated, as the same Agent. This is the
   safest reading of FR-22 (see owner question 1).
10. **REST acts refuse machine principals.** A fleet-run credential (or an integration key) calling
    `POST …/services/:name/:action` or `…/processes/:pid/signal` is refused (`refuseMachinePrincipalAction`): an
    Agent acts through its tools, where a risky act waits for its owner.
11. **`failedServices` (FR-7) is already fed on Linux** by FL-03's health probe (`systemctl list-units
    --state=failed`), so the services module does not duplicate it; macOS and Windows counts are a follow-up.
12. **Capability constants live with their types** (`FLEET_SERVICES_CAPABILITY` in `fleet-services.types.ts`,
    `FLEET_PROCESSES_CAPABILITY` in `fleet-processes.types.ts`) rather than in `fleet-jobs.types.ts` — both are
    exported from the same barrel.
13. **Signal settle time.** `processes.signal` waits 1.5 s (inside the link's 2 s inline window, so it never becomes
    an operation) and reports `stillRunningAfterMs`; the page offers "still running — Kill?" 5 s after Stop (S8).
14. **Palette rows are built from capability tags** (`services`, `docker`, `processes` — advertised only under
    `--manage`), so "Services on build-01" appears only for a computer that can answer it.

15. **Bind-mount sources use the one allowed-roots resolver (R-39).** FL-14's
    `apps/node/src/core/link/allowed-roots.ts` (landed while P2 was open) gives the lexical roots — workspace,
    `ready` checkouts, owner-listed roots; the Docker module's `bindSourceAllowed` adds the symlink check the resolver
    leaves to its caller: the source must exist and its REAL path must sit under a root's real path.
16. **Docker run is allow-listed end to end.** `validateFleetRunRequest` (contracts) runs on the web (dialog),
    the platform and the machine; there is no free-form flag, so privileged mode, host namespaces and cap-add cannot
    be expressed, and keys that ask for them are refused with the U13 sentence. Mounts use `--mount type=…,source=…`
    (key=value, no `:` / `,` splitting). Environment values travel ONLY through the Docker CLI's environment (`-e NAME`
    on the command line), names the CLI itself reads (`PATH`, `DOCKER_*`, loader variables) are refused, and every
    output line has the values masked and the secret scanner applied.
17. **Long Docker acts are FL-02 operations.** `docker.run`, `docker.image.pull` and `docker.image.prune` stream
    their output through `context.progress` (pull percentage across layers), so the machine family turns them into
    operations after the 2 s inline window; the platform answers 202 `{ operationId }` at once
    (`awaitOperationMs: 0`) and the web follows FL-02's record on an `OperationCard`. The node caps them at 5 at once
    (`busy`) and 60 minutes each. The audit row is written when the act starts (`outcome: ok` + `operationId`); its
    final state lives in the operation record.
18. **A prune with nothing to remove runs nothing and writes no row** (U15): the node answers `nothingToDo` before
    starting, and the service skips the audit for that answer.
19. **Agent Docker acts:** start / stop / restart and pull run as the Agent; container remove, image remove, prune and
    every `fleet_docker_run` are held as Approvals. An Agent's run request may carry environment variable NAMES only
    (empty values) — a held proposal is stored, and a stored row must never carry a secret (FR-29); the owner sets
    values by running it from the dialog.

20. **Compose reads come from Compose; a request names a project, never a path.** `compose.list` / `describe` /
    `action` look the project up in `docker compose ls` and use the config files IT reports (`-f … --project-directory
    <dir of the first>`); `ps` works from the containers' labels, so a project whose files are gone still lists its
    containers and offers Down only (U14). `down` never passes `-v` (FR-34).
21. **Shell inside is an owner Session with a container target.** The `session.start` params gain an optional
    `container: { container, shell }` (contracts `parseFleetSessionContainerShell`, owner `shell` sessions only); the
    node runs `docker exec -it -e TERM=xterm-256color <container> <shell>` instead of the login shell. No column stores
    the target (no migration): restarting such a session starts a plain login shell (follow-up). Agents get no
    `fleet_docker_exec` yet — FL-04 FR-51 makes an Agent's sessions Agent sessions, which start as jobs, not on the link.
22. **The picture is drawn as the spec draws it**: a service LEFT of everything it depends on (longest-path layers,
    barycentre order, cycle-safe, deterministic), arrows coloured by the dependency (amber: `service_healthy` not yet
    healthy; red: down or absent). `GET …/docker/containers/:cid/shells` is an additive read beside the CONTRACTS
    §11.2 routes.

## Questions for the owner

1. **Agent trust level and held acts (FR-22).** Held machine acts go through the existing owner-approval seam,
   which requires a person (a guardrail may block, never approve). The spec says "unless the Agent's trust level
   allows it (AW-24)". Default built: always a person. Should a high AW-24 rung auto-approve a blast-radius act?
2. **MCP whitelist entries (T-18) are deferred to FL-19.** The MCP spec `whitelist-fleet-run-surface.spec.ts`
   requires every fleet GET on the MCP whitelist to be granted to fleet-run tokens; adding the services /
   processes lists would widen the run-token surface to every process list of the owner's machines. Default
   built: no MCP entries; the in-process Agent tools exist. Grant the reads to run tokens, or keep them off MCP?
3. **Agent tool catalogue (Capabilities tab).** `agent-tool-catalog.ts` is pinned to equal the assembled tool list
   in its spec; the machine tools are not added to the catalogue stub yet, so the Capabilities tab does not list
   them. Add them (and the spec stub) in FL-19?
5. **Agent `fleet_docker_run` with secrets.** Default built: an Agent may propose a run with variable names only;
   values are typed by a person in the Run dialog. Should held runs carry values in an encrypted field instead?
6. **`fleet_docker_exec` for Agents.** Default built: not offered (an Agent's shell would have to be an Agent session,
   started as a job). Wanted?
4. **launchd Stop on a `KeepAlive` job** sends SIGTERM and launchd restarts it. Default built: that is shown
   honestly (the row is running again). Should Stop `bootout` the job instead (which then needs the plist path to
   start it again)?
