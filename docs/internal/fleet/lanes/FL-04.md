## Decisions

(Numbered so later notes can refer to them.)

1. **Session link messages live in FL-04's `fleet-sessions.types.ts`, not in FL-02's `FleetLinkControlMessage`
   union.** `session.event` / `session.list` / `session.ack` are channel-0 _extension_ messages: putting them in
   `FLEET_LINK_CONTROL_TYPES` would route them to the registry's `onControl` instead of
   `FleetLinkRegistry.onNodeControl(type, …)`. A spec pins that they never collide.
2. **One session channel per attached viewer, one short-lived channel per control request.** CONTRACTS §3.3 opens
   the family with `{ sessionId, mode }`; FL-04 adds optional `kind` so the node can check `--manage` (owner) vs
   `--work` (Agent) before it opens (R-5), and re-checks against the daemon's own record. Verbs:
   `session.start|attach|input|resize|end|rename|restart|screen|answer` (`answer` refused until FL-05).
3. **CONTRACTS additions this lane must write into `CONTRACTS.md` in PR 1 (not done yet — see Next step):**
   §1.1 daemon block gains `storage?: 'ok'|'failing'` (spec U15); §3.3 session family gains the `session.screen`
   verb, the platform→node channel-0 `session.ack { sessionIds }`, `session.list` carrying `daemon`, the
   `session.notice` notices (`paused · resumed · drain · slow-viewer · size · replay`) and optional `reason` on
   `session.event exited`; §4.1 `FleetNode.sessionDaemon` (simple-json, FL-04 slot 00); §4.2
   `FleetSession.exitCode` (int null) and `startedBy` (varchar 80, `user:<id>|agent:<id>`).
4. **`daemonSessionId` = the platform's row id at start.** The node addresses by it; `(nodeId, daemonSessionId)` is
   unique. The column stays separate so a later node-originated session needs no migration.
5. **Owner-session starts write their row only after the node confirmed the process runs** (state `working`, no
   `starting` phase for owner sessions), under a per-node advisory lock that re-counts the eight-session limit; a
   start that lost that race ends the process it just started and answers `limit_exceeded`. No phantom rows, no
   deleted rows. Node events that beat the row are held 10 s and applied when it lands.
6. **Process exit → `ended (exit)`**, outcome from the exit code (spec U14), kept as the first outcome written
   (FL-05 may set one earlier). User/drain/kill-switch ends → outcome `cancelled`; lost/timeout → `unconfirmed`.
7. **Node state refusal code is `busy`** (paused / disabled / enrolling, FR-39) — CONTRACTS §8 has no node-state
   code; `busy` is the nearest ("exclusive thing held"). Question Q2.
8. **No pipe floor in the daemon.** The PTY is `@homebridge/node-pty-prebuilt-multiarch` (lazy require, the
   range pty-local ships, `^0.13.1`); without it the daemon reports `pty: missing` and the node withdraws
   `sessions` with the fix in words. Tests use test-only hosts (`__tests__/pty-test-kit.ts`: an in-memory PTY and
   a real child process over pipes).
9. **Latest versions:** `@xterm/headless` 6.0.0 and `@xterm/addon-serialize` 0.14.0 (latest) added to
   `apps/node`. **Held back:** `@homebridge/node-pty-prebuilt-multiarch` stays `^0.13.1` (0.14.1 is latest): the
   bundle (`apps/node/build.js`) reads the range from pty-local's manifest, so a bump changes the cloud terminal
   host too, and the native prebuild cannot be proven here (the workspace never builds it — it is not in
   `onlyBuiltDependencies` — and fetching it is a download this lane may not make). Retry with a proven install.
10. **Owner session folders** must be inside the home folder or an extra root (plan §11); `~` expands; symlinks
    resolved. Windows compares without case. A Windows `.cmd`/`.bat` CLI never gets the first message on its
    command line (cmd.exe would re-parse `& | ^ %`): it is typed into the session 1.5 s after start.
11. **Daemon wire:** frames `[kind u8][len u32][payload]` (CONTRACTS §3.2 kinds without the channel), token-first
    hello (constant-time, re-read per hello, 4 KiB cap before auth, pipelining refused), control vs attach
    connections; every control connection counts as "a node connected" for the idle rule.
12. **Sessions tag is dynamic:** the runtime now re-reads module tags on every beat (`currentEnvironment()` in
    `runtime.ts`), so `sessions` follows the daemon's health (FR-10). `sessions` is non-selectable like `managed`.
13. **Heartbeat tier:** `daemon` is the newest strip tier; `describeStrippedTiers` now names the fields dropped
    instead of the tier index.
14. **`NodeLink.sendControl`** added (additive, FL-02's file) so a module can send channel-0 messages that belong
    to no channel; the session module binds the link via `bindLink(link)` (runtime) for facts, kill switch, drain.
15. **Windows service:** NSSM `AppKillProcessTree 0` (T-19), tested in `test-install-service-logic.ps1`.
    **systemd unit left unchanged** (its default `KillMode=control-group` and `ProtectHome=read-only` apply to the
    daemon); documented in `apps/node/packaging/README.md`. Question Q1.
16. **End needs `confirm: true`** (CONTRACTS §2.2 class `confirm`); without it `confirmation_required` with the
    summary "End "<title>" on <computer>? The process is stopped; its screen is kept."

17. **List routes answer a page object** — `FleetSessionListResponse { sessions, nextCursor, recentFolders? }`
    (contracts), not a bare array: the keyset cursor (`<lastActivityAt>|<id>`) needs a place, and the node route
    carries the start dialog's recent folders in the same read.
18. **`restartOf` on the start route** goes through `FleetSessionService.restart(..., { expectNodeId })`: a session
    of another computer answers `invalid`, never a restart elsewhere.
19. **`FleetLinkService.liveConsents(nodeId)`** added (additive, FL-02's file): this replica's link, else the holder's
    directory entry — the start gate reads the consents the machine runs with now.
20. **`FleetSessionsApiModule` is `@Global()`** (the `FleetLinkApiModule` precedent): the agent-side
    `FleetSessionsModule` consumes `FLEET_SESSION_NODE_PORT` `@Optional()`, and the trigger-internal controller
    reaches `FleetSessionSweepService` through it.
21. **Node reports are applied in arrival order per node** (`FleetSessionLinkListener` queues per node id), so an
    `exited` never overtakes its `started`; different nodes run in parallel. Reports are handled only on the replica
    that holds the link (FL-02), and dropped while `FLEET_SESSIONS_ENABLED` is off.
22. **Sweeper schedule `4-59/5 * * * *`** (`FLEET_SESSION_SWEEP_CRON`, contracts) — plan §10's `4/5`, spelt as a range
    every cron parser reads; the Trigger task and the API fallback cron (`FleetSessionSweepCronService`, gated on
    `!shouldUseTrigger()`, task-locked) share it.
23. **CodeQL 276** (polynomial regex on the folder title): `fleetSessionFolderTitle` is a linear scan.

### P1b (2026-10-21, PR #2830)

24. **The viewer path is FL-02's gateway, observed — no `session.family.ts`.** FL-02's
    `FleetLinkViewerGatewayService` gained per-family observers (`registerObserver(family, observer)`:
    `admit` → `opened` → `inbound(bytes)` → `stillAllowed` on every 30 s ping → `closed`, additive). FL-04's
    `FleetSessionPresenceService` is the `session` observer: the five-viewer cap (a slot is reserved at admit,
    so simultaneous opens cannot all pass), one `node.session.attach` row when a channel opened, ONE
    `node.session.input` row per driver span (`from`, `to`, `bytes` — payload bytes only) when a driver that
    typed closes, and the audience re-check (`FleetSessionService.canStillSee`; a refusal closes `4013`, a
    database that cannot answer keeps the viewer).
25. **Presence is per API replica** (in memory). Behind several replicas a session's browsers may be split and
    the cap counted per replica; the daemon fans out to every channel either way, so the cap is a courtesy
    limit, not a boundary. Question Q4.
26. **The `session` family's JSON allow-lists (CONTRACTS revision 8).** A watcher may send `session.attach`
    and `session.screen`; a driver `session.attach|input|resize|screen` (new
    `FLEET_LINK_DRIVER_JSON_TYPES`, a family absent there forwards everything as before). The relay refuses
    a driver's `session.start|end|rename|restart|answer` on the live view (`viewer.refused`), so those acts only
    happen through the §11.2 routes with their confirmation and audit.
27. **A watcher is admitted under the kill switch** (`canAttachFleetSession` gained an optional `role`; absent =
    driver = the P1 reading): it reads the stop banner; a driver is refused `kill_switch`, and the link's own
    gate refuses a driver channel (state-changing) anyway.
28. **The browser sends `session.attach { cols, rows }` after `viewer.ready`** (the node attaches only on that
    request); the attach token carries `{ sessionId: daemonSessionId, kind }` as channel params and the gateway
    adds the role as `mode`.
29. **Web: BFF routes, not server actions** (plan §8) — every body rebuilt from an allow-list
    (`lib/api/fleet-sessions-bff.ts`), the CONTRACTS §8 envelope passed through, so dialogs mark the field an
    `invalid` names and cards list what a `limit_exceeded` names. The Terminal pane gained
    `source: { kind: 'fleet-session', sessionId }` (R-21) on top of the same `FleetSessionSocket` the session page
    uses; the page itself composes `useSessionAttach` + `SessionTerminal` for the richer states.
30. **Default role on the page**: the person who started an owner session drives; everyone else watches and may
    "Take the keyboard" (several drivers allowed, decision A8 default). Role switch = a fresh token, no reload.
31. **Copy link** copies the bare route (`/fleet/sessions/<id>`): sessions are a person's own, so the reader's
    locale and personal scope resolve it.
32. **Readiness** lists `fleet: { sessions }` (T-48).

### P2 (2026-10-21, PR #2837)

33. **An Agent session is a durable `agent-session` job** pinned to the node it was started on (R-28), its session row
    `starting` while the job waits for a slot (the page says "Waiting for a free slot on build-01…" and does not
    attach), its Run (trigger `session`) created before the job and linked both ways (`fleet_sessions.agentRunId`,
    `agent_runs.fleetSessionId`, migration `1796040100000`). Order: row → Run → job, so the Run's FK finds its
    session; a start that cannot be queued ends the row and fails the Run (`markDispatchFailed`).
34. **Queue SLA 2 h, not plan T-33's 600 s.** The per-kind default doubles as the fallback an unknown kind fails closed
    to (the SHORTEST default — pinned by the contracts spec), so a 600 s default would have changed every unknown kind;
    the live-view kind made the same choice. The ten-minute limit lives in the session sweeper instead
    (`FLEET_AGENT_SESSION_QUEUED_TIMEOUT_MS`, `findAgentStartingBefore`), which also withdraws the job and fails the Run.
35. **Ending either ends both (R-1).** `end` withdraws the job (`cancelForSession`, found by the idempotency key
    `fleet-session:<id>` — no job-id column) and cancels the Run; a node report that ends the session settles the Run
    by its outcome; the API's `AgentSessionJobListener` ends a still-live row when the job settles and marks the Run
    running when it is leased (a lease of an ended session is withdrawn at once).
36. **Agent sessions run on the person's own computer** (`node.userId === actor.userId`, else `unsupported_on_node`):
    a node leases only its owner's jobs, so an Agent session on an Organization-shared computer could never start.
    Question Q5.
37. **The isolation is the Task run's, reused — never downgraded.** `agent-task.ts` exports
    `establishModelContainment` / `refuseUnderClaudeManagedMcpConfig` / `scratchDirName` (additive) and the executor
    calls them unchanged; where a Task run would DOWNGRADE (run in the owner's real home with the reason recorded), an
    Agent session REFUSES `unsupported_on_node` with that reason. MCP: the empty strict config +
    `ENABLE_CLAUDEAI_MCP_SERVERS=false`; control 17 settings (no repository settings, no hooks); Codex
    `--ignore-user-config`. **Not yet:** the platform's MCP tool bridge for sessions (a session gets no platform tools)
    and the `agentProfile.ensure` browser profile — both follow-ups (Next step).
38. **Interactive argv**: Claude Code `--permission-mode <mode> --mcp-config <empty> --strict-mcp-config
    --setting-sources user --settings <fleet settings> [overlay] "<first message>"`; Codex `--ignore-user-config
    --sandbox workspace-write|read-only -C <cwd> [overlay] "<first message>"` (interactive, not `exec`). A Windows
    `.cmd` CLI gets its first message typed after start (decision 10's rule).
39. **First message**: stored redacted on the session row; the job payload carries it as typed (like a Task's prompt —
    redacting it would change the instruction).
40. **Tools act on the Agent's OWN sessions only** (list filters by `agentId`; read/send/rename/end refuse another
    session as `not_found`); `fleet_sessions_send` writes one `node.session.input` row per send (bytes only).
    MCP whitelist carries the five REST-backed tools (no REST input route — send is Agent-side only); a fleet-run token
    is refused all five.
41. **CLI** `ever-works fleet session list|attach` uses the global `WebSocket` (Node 22+) — no new dependency.
42. **T-50** needs no platform change: the job requires the CLI's tag, which `blockedByModelThrottle` already filters;
    the node excludes `agent-session` while every CLI is out of quota.

### P3 (2026-10-21, PR #2841)

43. **The recorder is a watch-only channel, not the viewer bridge.** T-42 said the family forwards `DATA` to the
    transcript "when recording"; but a session is recorded while NOBODY watches too, so the API's
    `FleetSessionRecorderService` opens its own `session` channel per recorded session (`mode: 'viewer'`, a system
    caller, never state-changing — the link's kill-switch and consent checks apply), asks the node to attach, and
    stores every `DATA` frame through `persistSessionFrames` (redacted, batched 1 s / 64 KiB). It runs only on the
    replica that HOLDS the node's link (one recorder per session, one sequence), and a 30 s sweep there picks up
    sessions whose recording was switched on through another replica. The sequence continues after the highest stored
    `seq`, so a re-attach appends; a `replay` notice is stored as a terminal reset (`ESC c`) so the player clears there
    as a live viewer does. `FleetSessionService` is resolved through `ModuleRef` in the recorder: the service consumes
    the recorder's port, so a constructor dependency back would be a provider cycle.
44. **Defaults (FR-54):** Agent sessions recorded; owner sessions when the node's `recordWatchSessions` is on; any live
    session can be switched from its footer (`POST /sessions/:id/recording { on }`, one
    `node.session.recording.start|stop` row; the kill switch does not refuse it — the recorder only watches). A session
    that ends while recording becomes `stored`; a storage failure turns recording `off` with one audit row
    (`outcome: 'storage-failed'`) and never touches the live view.
45. **Retention 14 days whatever the plan** (`FLEET_SESSION_RECORDING_RETENTION_DAYS`); the nightly
    `terminal-transcript-gc` calls `sweepExpiredSessions()` after the run sweep (an older API answering an error is
    logged, the run sweep is already done). The manifest says `expired` for an ended, recorded session with no chunks
    left after the window.
46. **Manifest and pages on the CONTRACTS §11.2 path** (`GET /sessions/:id/recording`, `?from=&limit=` for a page — no
    sub-route); driver spans come from the last 200 audit rows of the node (`node.session.input` with this session as
    target). The player shortens idle gaps to 3 s and maps the spans onto that clock.
47. **The user doc (T-46) is folded into this PR** (`docs/features/fleet-sessions.md`, sidebar entry, cross-links from
    `fleet.md` and `agent-terminals.md`); AW-11's tracker row and its T50 / T55 tasks point here (T-47).

## Questions for the owner

(Also OWNER-QUESTIONS A7, A8, B3 — the three open epic questions; their defaults are built: owner sessions not
recorded by default, several drivers allowed, `pwsh` else Windows PowerShell.)

- **Q1 — Linux service installs.** Under the hardened `ever-works-node@.service` (system unit), a service restart
  kills the session daemon (cgroup kill) and `ProtectHome=read-only` keeps owner sessions from writing to home.
  Options: ship a drop-in with `KillMode=process` + `ProtectHome=false` (a crashed node then leaves job processes
  behind, which the existing quarantine gate catches), or document running the node as a `systemctl --user`
  service for machines that host owner sessions. Built: unit unchanged, README says so.
- **Q2 — refusal code for a paused / disabled node** (FR-39): built `busy` with `details.nodeState`. A dedicated
  code would be a CONTRACTS §8 change.
- **Q3 — `onlyBuiltDependencies`.** The workspace never builds the PTY addon, so a node run from the monorepo
  (not the npm bundle) never advertises `sessions`. Adding the addon to `pnpm-workspace.yaml`
  `onlyBuiltDependencies` would make every install download its prebuild. Built: unchanged.

- **Q4 — viewer presence across API replicas.** The five-viewer cap and the footer's watchers are counted per
  API replica (decision 25). Sharing presence on the relay bus would make the cap exact; built: per replica.

- **Q5 — Agent sessions on Organization-shared computers.** A node leases only its owner's jobs, so P2 refuses an Agent
  session on a computer the person does not own (decision 36). Widening the lease to the session's node (whoever
  started it, inside the `sessions` audience) is a lease-protocol change.
