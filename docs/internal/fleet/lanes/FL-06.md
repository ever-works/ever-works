## Decisions

1. **The pure rules live in `@ever-works/contracts`** (`fleet-session-actions.types.ts`): the branch rule
   (`proposeFleetSessionBranch`, reusing FL-14's `proposeFleetCheckoutBranch` for the suffix), the Changes reply parser
   (it re-applies the caps), the seven default templates, `renderFleetSessionActionPrompt`, the relevance truth table
   (`availableFleetSessionActions`), the typed bytes of a prompt. The web menu, the dialog and the server read the same
   functions (plan §3 "one truth table").
2. **The session view carries its checkout** (`FleetSessionView.git`, CONTRACTS rev 20): one batched read of the
   sessions' checkouts in `FleetSessionService.withTasks` and the board — no new column (spec §6 Compatibility).
3. **The node never knows the pull request**: its git line always says `pr: null`, so FL-14's fold would wipe the
   platform's answer every refresh. `withKnownPullRequest` (checkout policy) keeps the resolved `pr` while the branch is
   the one it was resolved for; a branch change drops it until the enrichment resolves the new one.
4. **The pull-request half is the API's** (`apps/api/src/fleet/session-git/`), not `packages/agent/src/fleet/` as plan
   §4 says: it needs the GitHub App credentials and `FleetPushCredentialService` (the installation-scope resolver),
   both API-side. `FleetCheckoutService.setPullRequest` stays the one writer of `fleet_checkouts`.
5. **Credentials for the provider**: an installation token of the Node owner's GitHub App installation, narrowed to the
   one repository (`describeScope` → `requestGitHubAppInstallationAccessTokenDetails` with `repositoryIds`, the
   installation's own permissions — naming permissions the App may not hold would fail the mint), reused until 5 min
   before it lapses, never logged; without an installation, the owner's own connected GitHub account through the git
   facade. An ssh / scp remote is matched through its `https://github.com/owner/repo` form.
6. **"Unresolved review comments"** = review comments on the open pull request still anchored to a line (`line !==
   null`); an outdated comment (its line gone after a later push) counts as addressed. The provider contract has no
   thread-resolution read (question Q2).
7. **The cadence and the enrichment are one API cron** (`FleetSessionGitCronService`, every minute, distributed lock),
   whatever the job runtime: the enrichment keeps mergeability and comment counts in-process for a minute (plan §4),
   and the credentials are the API's. A Trigger.dev twin (`fleet-pr-enrichment`) and the `github.pr` ingest nudge are
   follow-ups (Next step). Live-session checkouts are asked every minute, checkouts with only a recent pull request
   (≤ 7 days) every ten, at most 80 provider asks per tick.
8. **"Once when it stops"** (FR-11) = the first tick after a session leaves `working` (its `stateChangedAt` within the
   last 90 s), remembered per process so it runs once; `needs_you` is not `working` (the agent is not changing files).
9. **`GET /sessions/branch-proposal` sits on FL-04's sessions controller, above `sessions/:id`** — in its own controller
   Express could match `sessions/:id` first and `ParseUUIDPipe` would answer 400. The service is reached through the
   global `FleetSessionGitApiModule` (`@Optional()` on the controller).
10. **`checkouts.changes` needs `work-or-manage`** (a `FLEET_LINK_VERB_CONSENT_OVERRIDES` entry): a Task's worktree
    reads under `--work`, anything else needs `--manage`, checked on the machine and narrowed by the platform. It is a
    read (`stateChanging: false`) but both the platform and the verb refuse it under the kill switch (spec U3).
11. **The Where step creates first, then starts** (FL-15 decision 3's one create path): New worktree / Fresh clone go
    through FL-14's `POST /api/fleet/checkouts` with the proposed branch, the dialog waits for `ready` (≤ 2 min), then
    FL-04's start runs with `checkoutId`. A Task's branch is read-only in the field (FR-4).
12. **A prompt is typed as one line and one Enter** (`fleetSessionActionInputBytes`): newlines fold into spaces (a
    terminal agent reads a bare Enter as "send"), control characters are dropped — bracketed paste was not used because
    a CLI that did not enable it would print the escape codes.

13. **P2 — the delivery confirmation is the link's reply**: `session.input` resolves when the node's daemon took the
    bytes, so a send is `delivered` at once and `undelivered` when the link could not confirm it (unreachable, timed
    out). No echo watcher and no sweep task (T-16): a ledger row still `pending` 5 s after it was sent READS as not
    delivered. Re-sending is only offered for one that was not delivered, as a NEW entry (`resendOf`), never twice
    silently.
14. **P2 — one audit row per send is `node.session.action`** (CONTRACTS §7 wins over the spec's "`node.session.input`
    with the action named"): `FleetSessionService.typeAction` types without writing its own `node.session.input` span.
    The ledger row never stores the prompt; the audit row a redacted 200-character preview. An owner session's ledger
    is its `node.session.action` + `node.session.pull-request.open` rows (R-38); cost "session total only".
15. **P2 — the rate is per API process** (10 a minute, 2 s apart per session, `busy` naming the last sender); a
    multi-replica deployment can let one extra through (same posture as FL-14's write rate).
16. **P2 — in an owner session "Open a pull request" is the dialog**, not a prompt (FR-18): the CLI of an owner session
    holds no run token, so it could not call the tool; the platform opens it. A direct send is refused `invalid` (rule
    `owner-dialog`).
17. **P2 — updating a pull request needed a provider capability**: `updatePullRequest?` on the git provider contract
    (optional), the GitHub plugin (`pulls.update` with only title / body) and `GitFacadeService.updatePullRequest`
    (`GitOperationNotSupportedError` when absent). Nothing touches state, base, head or merge.
18. **P2 — a Task-bound session opens through the Task's own finalize** (`TaskWorkspaceService.finalizeRemotePush`,
    reached with `getOptionalProvider` so this module does not import the Tasks module): the Task records the pull
    request and moves to In review exactly as a Task run (FR-19); its title comes from the Task, not the request. Any
    other session opens through the GitHub App (`createPullRequest`) with the redacted title and body.
19. **P2 — a run token reaches exactly two new routes** (`GET`/`POST /api/fleet/checkouts/{id}/pull-request`, the
    `FLEET_RUN_TOKEN_ROUTES` allow-list); the POST refuses a checkout that is not the run's own session's, and an
    Agent without "may open pull requests" (`permission_denied` naming the permission, U11). The actions routes are
    NOT on the list, so a run token never sends actions.
20. **P2 — the relevance facts come through a port** (`FLEET_SESSION_PR_FACTS`, bound to the API's enrichment service):
    unbound, fix-comments and resolve-conflicts stay hidden (the safe reading).

21. **P3 — Clean up is FL-14's delete with `?cleanUp=1`** (no new route, no second delete tool): the gate now also
    refuses while a live session uses the worktree (`invalid`, rule `live-session`, FR-25), before the changes-check;
    the branch is always kept. The button decides visibility from the same rule (`canCleanUp`); the checkout row reads
    "a session uses it" from the node's `busy` fact.
22. **P3 — the Agent tools** (`buildFleetSessionGitTools`) are bound by the API next to FL-14's
    (`sessionGit: { actions, checkouts, pullRequests }`), classified on the trust ladder (`fleet_sessions_actions_list`,
    `fleet_checkouts_changes` read; `fleet_sessions_action` write.internal; `fleet_checkouts_open_pull_request`
    publish.external) and listed in the catalogue; an Agent's own tool call to open a pull request carries its id, so
    its "may open pull requests" permission applies in-process too.
23. **P3 — MCP** gains five entries (`fleet_sessions_actions_list`, `fleet_sessions_action`, `fleet_checkouts_changes`,
    `fleet_checkouts_pull_request_get`, `fleet_checkouts_open_pull_request`); the CLI `fleet session actions|action`,
    `fleet checkout changes|pull-request`, and `--clean-up` on `fleet checkout delete`.
24. **P3 — the Fleet actions editor goes through the API** (`GET/PUT /api/fleet/agents/:agentId/action-templates`): the
    web has no YAML library and a new dependency is off-limits, so the platform reads and writes the `fleet` block with
    the YAML document API (the rest of the file, comments included, kept) and saves through `AgentFileService.write` —
    ownership, secret scan, size cap, etag and the activity record exactly as the editor's own save. A template equal
    to the default is not stored.
25. **P3 — the branch proposal honours `fleet.branchPrefix`** (the Agent's own prefix, else its slug).

## Questions for the owner

- **Q1 — Trigger.dev twin.** The enrichment runs as an API cron even when Trigger.dev is the job runtime (decision 7).
  Add the `fleet-pr-enrichment` Trigger task anyway?
- **Q2 — unresolved comments.** Built as "still anchored to a line" (decision 6). Add a provider read of review-thread
  resolution (GraphQL `reviewThreads.isResolved`) to the git provider contract?
- **Q3 — the per-session git credential (T-19, not built).** An Agent session pushes with what its environment
  has: the machine's own login for a worktree of the owner's clone. A worktree of a clone Ever Works made needs a
  per-session credential helper that answers `git credential fill` with a run-scoped token while the lease lives — and
  the platform's push-credential mint does not cover `agent-session` jobs yet (it is scoped to Task jobs' repositories).
  Build both (node helper + an `agent-session` scope on the push credential), or keep sessions on the owner's login?
- **Q4 — the PR gate for free sessions.** The quality-gate check (`PullRequestGateService`) is Work-scoped; a session
  outside a Task opens its pull request without it (a Task-bound one goes through the Task's own gate). Apply the
  Work's gate when the checkout is linked to a Work?
- Spec §8b questions (org-wide templates, owner-session prefix override, Codex worktree writes, owner push to a
  protected branch) — defaults built as the spec states.
