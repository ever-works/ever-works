## Decisions

1. **The pure rules live in `@ever-works/contracts`** (`fleet-task-handoff.types.ts`): eligibility reasons, the
   first-message builder, the GitHub source link parser, the default checkout choice. The web dialog and the API read
   the same functions, so the dialog and the server can never disagree on why a computer is not selectable (plan §15
   risk 1).
2. **The options service lives in the API** (`apps/api/src/fleet/tasks/`), not in `packages/agent/src/fleet/` as plan
   §4 says: it reads `TasksService.listRunCandidates` (the exact resolver **Run with agent** uses, FR-4), which sits in
   `TasksDomainModule`; importing that into an agent-side fleet module would risk a provider cycle. The start-time
   checks (Task visible, `busy`, pin, slot) live agent-side in `FleetSessionTaskService`, consumed `@Optional()` by
   `FleetSessionService`, so every caller of the one start path (REST, tools) gets them.
3. **A start may now name `checkoutId`** (the FL-14 follow-up): the session runs in that checkout's folder (`cwd` =
   its path), on the same computer, only when the checkout is `ready` and `host`-isolated; a container checkout is
   refused `unsupported_on_node` until FL-04 spawns through `containerArgvFor` (FL-14 decision 19). Owner and Agent
   sessions both accept it. `newWorktreeOf` stays refused: the dialog creates the worktree through FL-14's
   `POST /api/fleet/checkouts`, waits for `ready`, then starts in it with `checkoutId` — one start path, one create
   path.
4. **The Run of a Task session keeps `triggerKind: 'session'`** and gains `taskId` + `workId` (denormalised as
   assign-task does), so the Task's run history, the board's in-flight checks and `findInFlightForTaskAgent` see it.
5. **`busy` = a queued or running Run for (Task, Agent)** (`AgentRunRepository.findInFlightForTaskAgent`), the same
   dedup assign-task uses; the refusal names the session when the Run is a session's.
6. **The pin is respected, never written** (FR-3): an Agent pinned to another computer is refused `invalid` with the
   hint naming the pinned computer; `FleetAgentNodeAffinityService.setAffinity` is never called. Affinity is read
   through `FleetAgentNodeAffinityRepository.findForAgent` (it needs the Agent's Organization; an Agent without one is
   unpinned).
7. **No free slot** = the computer already runs as many live Agent sessions as its `effectiveMaxConcurrentJobs`;
   only a Task hand-off is refused (`limit_exceeded`, spec U5) — a plain FL-04 Agent session still queues, unchanged.
8. **Closed-set reasons gain `no-access`** (an organisation member outside the computer's `sessions` audience, or a
   computer that belongs to someone else — FL-04 decision 36 runs Agent sessions on the person's own computers only).
   Spec FR-2 lists six reasons; this seventh is additive (question Q1).
9. **The Agent's CLI** is derived from its AI provider: an OpenAI provider → Codex, anything else → Claude Code
   (`fleetHandoffAgentCli`). A computer without that CLI is `missing-cli` (spec U6).
10. **The Task source link (P1)** is parsed from the Task description (the Trigger prompt writes it there); the
    structured PR facts from the Trigger fire arrive with P3 (T-16).
