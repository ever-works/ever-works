## Decisions

1. **The pure rules live in `@ever-works/contracts`** (`fleet-task-handoff.types.ts`): eligibility reasons, the
   first-message builder, the GitHub source link parser, the default checkout choice. The web dialog and the API read
   the same functions, so the dialog and the server can never disagree on why a computer is not selectable (plan §15
   risk 1).
2. **The options service lives in the API** (`apps/api/src/fleet/tasks/`), not in `packages/agent/src/fleet/` as plan
   §4 says: it reads `TasksService.listRunCandidates` (the exact resolver **Run with agent** uses, FR-4), which sits in
   `TasksDomainModule`; importing that into an agent-side fleet module would risk a provider cycle. The start-time
   checks (Task visible, `busy`, pin, slot) live agent-side in `FleetSessionTaskService`, consumed `@Optional()` by
   `FleetSessionService`, so every caller of the one start path (REST, tools) gets them.
3. **A start may now name `checkoutId`** (the FL-14 follow-up): the session runs in that checkout's folder (`cwd` =
   its path), on the same computer, only when the checkout is `ready` and `host`-isolated; a container checkout is
   refused `unsupported_on_node` until FL-04 spawns through `containerArgvFor` (FL-14 decision 19). Owner and Agent
   sessions both accept it. `newWorktreeOf` stays refused: the dialog creates the worktree through FL-14's
   `POST /api/fleet/checkouts`, waits for `ready`, then starts in it with `checkoutId` — one start path, one create
   path.
4. **The Run of a Task session keeps `triggerKind: 'session'`** and gains `taskId` + `workId` (denormalised as
   assign-task does), so the Task's run history, the board's in-flight checks and `findInFlightForTaskAgent` see it.
5. **`busy` = a queued or running Run for (Task, Agent)** (`AgentRunRepository.findInFlightForTaskAgent`), the same
   dedup assign-task uses; the refusal names the session when the Run is a session's.
6. **The pin is respected, never written** (FR-3): an Agent pinned to another computer is refused `invalid` with the
   hint naming the pinned computer; `FleetAgentNodeAffinityService.setAffinity` is never called. Affinity is read
   through `FleetAgentNodeAffinityRepository.findForAgent` (it needs the Agent's Organization; an Agent without one is
   unpinned).
7. **No free slot** = the computer already runs as many live Agent sessions as its `effectiveMaxConcurrentJobs`;
   only a Task hand-off is refused (`limit_exceeded`, spec U5) — a plain FL-04 Agent session still queues, unchanged.
8. **Closed-set reasons gain `no-access`** (an organisation member outside the computer's `sessions` audience, or a
   computer that belongs to someone else — FL-04 decision 36 runs Agent sessions on the person's own computers only).
   Spec FR-2 lists six reasons; this seventh is additive (question Q1).
9. **The Agent's CLI** is derived from its AI provider: an OpenAI provider → Codex, anything else → Claude Code
   (`fleetHandoffAgentCli`). A computer without that CLI is `missing-cli` (spec U6).
10. **The Task source link (P1)** is parsed from the Task description (the Trigger prompt writes it there); the
    structured PR facts from the Trigger fire arrive with P3 (T-16).
11. **The dialog talks to the platform through Server Actions** (`app/actions/fleet-task-handoff.ts`, the FL-14
    precedent) for the options and the checkout it waits on, and through FL-04's session BFF route for the start
    (`sessionsClient.start`, `taskId` now on its allow-list). Plan §8's BFF route
    `app/api/fleet/tasks/[id]/handoff-options` is not needed.
12. **A checkout already on the Task's branch is reused** (the dialog's default): a second worktree would get a suffixed
    branch from FL-14's never-reuse rule and leave the Task's branch (FL-06 Task-branch reuse).
13. **The Task page pieces are server components passed into `TaskDetailClient`** (`fleetAction`, `fleetSection`
    props): `FixOnComputerSlot` (flags + at least one computer) and `TaskFleetSection` (latest session, computer,
    Agent, checkout). The board reads one server gate (`FleetTaskHandoffGate`) through a context, so the cards need no
    new props.
14. **A restarted Task session keeps its Task** (the Run of the ended session names it), and a Task start is refused
    on owner sessions (`invalid`: a Task is handed to an Agent session).

15. **P2 — only the computer's owner sets its git identity.** The identity is the person's own (display name +
    GitHub no-reply address), and the global config is the enrolling user's; a member in the computer's `commands`
    audience is refused `permission_denied` (spec U4 says the fix "follows the commands family's audience" — the
    safer reading is built; question Q3). The read follows the `view` family with values masked for non-owners.
16. **P2 — the identity service lives agent-side** (`packages/agent/src/fleet/git/`, `FleetGitModule`) over FL-09's
    `FLEET_MACHINE_NODE_PORT` (the link gate: existence, kill switch, `--manage`, family audience), so P3's Agent tools
    can call it. "Can push for agents" = the node's `git-push` tag and at least one repository in the owner's
    (non-deleted, non-suspended) GitHub App installations; the card names up to five.
17. **P2 — the node module is one entry in `NODE_LINK_MODULES`** (`createGitModule()`, R-40): `git.identity` (read)
    and `git.setIdentity` (state-changing, so the link refuses it while paused); both need `--manage` through the
    contracts consent table. Values are argv elements of `git config --global`, control characters and leading dashes
    refused, emails shape-checked.

18. **P3 — the audience is an additive key of the `simple-json` matcher** (`eventMatcher.audience.me[]`, no
    migration). A matcher still needs `source`, `kind` or `workId`; the audience only narrows it, OR across its kinds,
    against the owner's linked GitHub login read once per event (`GitHubAppUserLinkRepository`), case-insensitively;
    with no login nothing matches (fail closed). Creating or updating a matcher with an audience is refused 400 without
    a linked account (spec U11 says `invalid`; the Triggers surface answers plain HTTP 400 like its other refusals).
19. **P3 — the PR intake is a third registered consumer on the one GitHub dispatcher** (`GitHubPrIntakeService`):
    `opened` and `synchronize` stay the review bridge's (no duplicate events); the intake's subject is the bridge's
    `<owner/repo>#<number>`, so subject coalescing treats both as one pull request.
20. **P3 — coalescing updates the existing Task (U12)**: an audience Trigger's subject marker remembers the Task it made
    (`inbound_trigger_fires.taskId` on the marker row), and a coalesced event posts one chat line on that Task
    (`TaskChatService.post`, best effort). The description is not rewritten (the chat line carries the event and its
    link). The preset uses the longest replay window so a review re-request lands on the same Task.
21. **P3 — a pull-request Task works on the pull request's head**: the hand-off reads the Trigger fire that made the
    Task → the ingested `github.pr` event → `headRef`, `headRepo`, `fork`, `maintainerCanModify`; the checkout default
    becomes a fresh clone of the head repository on `headRef` (FL-14's worktree always cuts a NEW branch); a fork
    without maintainer edits is marked read-only in the dialog (nothing on the machine enforces it yet — Q4). A Task
    with no such fire keeps its own branch; resolving a description-only PR link through the GitHub App is not built.
22. **P3 — the tools**: `fleet_tasks_handoff_options` (read), `fleet_nodes_git_identity_get` (read),
    `fleet_nodes_git_identity_set` (`confirm`, `write.internal` on the trust ladder), and `taskId` / `checkoutId` on the
    existing `fleet_sessions_start` (no second start tool). `FleetTasksApiModule` is `@Global()` so the API's
    AgentsModule resolves the two services optionally. MCP adds the same three names plus
    `inbound_triggers_github_for_me`; the CLI adds `fleet session start --task` and `fleet nodes git-identity`.

## Questions for the owner

- **Q1 — a seventh reason.** `no-access` covers "outside the computer's `sessions` audience" and "someone else's
  computer" (Agent sessions run on your own computers only). Keep it, or fold it into one of the six?
- **Q2 — Agent CLI choice.** Built: derived from the Agent's AI provider (OpenAI → Codex, else Claude Code). Should
  an Agent carry an explicit preferred CLI?
- **Q3 — who may set a computer's git identity.** Built: the owner only (decision 15). Should an organisation admin in
  the `commands` audience be able to set it to THEIR identity on someone else's computer?
- **Q4 — fork pull requests.** Built: the dialog says "From a fork — the Agent can review and comment but not push"
  when the fork does not allow maintainer edits; nothing stops a push on the machine. Should the session's push
  credential refuse a fork's branch?
- Spec §8b questions (fork pushes, "for me" auto-start) — defaults built as the spec states: no same-repo branch is
  proposed for a fork; the preset parks in the Backlog (`autoStart: 'manual'`) unless the caller asks for `always`.
