# App spec — rule → enforcement map

**Artifact:** `docs/specs/features/app-works/_build-artifacts/apw-03-schema/validator-rules.md`
**Companion:** [`app-spec.schema.json`](./app-spec.schema.json) (the artifact), [`evidence/`](./evidence) (the proof),
[`gaps-and-contradictions.md`](./gaps-and-contradictions.md) (what is still open)
**Built against:** [`schema.md`](../../APW-03-app-spec-and-catalog/schema.md) and
[`CONTRACTS.md`](../../CONTRACTS.md) as they stood at the run recorded in
[`evidence/run-transcript.txt`](./evidence/run-transcript.txt) (HEAD `e47866dc7` plus uncommitted
worktree edits; every fixture's sha256 is in the transcript).

This document answers one question for the implementer: **for each rule in `schema.md`, which layer
enforces it, and what exactly does that layer say?** Every rule is mapped either to a JSON Schema
construct inside `app-spec.schema.json` or to a named imperative check with its `APP_SPEC_ISSUE_CODES`
code and its exact condition. Rules that cannot be anything but imperative are marked as such, with the
reason, so nobody spends a day trying to express them as JSON Schema.

## 0. The three enforcement layers

`schema.md` §2–§3 already implies three layers; this artifact makes them concrete.

| #   | Layer             | Lives in                                                                                                          | Sees                                                                                                                       | In this artifact                                                                                |
| --- | ----------------- | ----------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| 1   | **Text pipeline** | `validateAppSpecDocument(text, …)` (plan.md §2.2, [`plan.md:131-142`](../../APW-03-app-spec-and-catalog/plan.md)) | bytes, YAML syntax, positions                                                                                              | **not here** — no JSON Schema can see a file size, an alias count or a duplicate mapping key    |
| 2   | **JSON Schema**   | the `app` branch of `works.v2.schema.json` and the stand-alone `app-spec.schema.json`                             | the parsed document's _shape_: types, enums, bounds, presence, `oneOf`, and the cross-field rules an `if`/`then` can reach | **[`app-spec.schema.json`](./app-spec.schema.json)**, applied by `Ajv2020` (draft 2020-12)      |
| 3   | **Rule engine**   | `app-spec.rules.ts` + `app-spec.refs.ts` + `app-spec.issues.ts` (plan.md §2.2)                                    | the _document as a whole_ and the platform: references, graphs, detection, plugin availability, account state              | specified in §2 below; the checks the evidence runner implements are in `evidence/validate.mjs` |

Nothing in layer 3 is redundant with layer 2: where a rule is schema-expressible, the schema carries it
and layer 3 does not repeat it (that is why `neg-03`, `neg-10`, `neg-11`, `neg-12`, `neg-25`, `neg-26`
fail layer 2 and pass layer 3 in the transcript). Where both carry the same rule, it is because the
schema can only see the _shape_ while the issue object needs an issue **code and a path** — that is the
whole content of §5.

### The skeleton, in one line

```
root (loose: unknown keys preserved)  →  spec  →  appSpec (strict: unknown keys are errors, x- exempt)
```

- Root keys mirror the committed envelope — `works.v2.schema.json:6-67` for the v1 keys, whose shapes are
  reproduced unchanged (`version`, `kind`, `name`, `title`, `initial_prompt`, `model`, `website_repo`,
  `schedule_cadence`, `deploy_provider`, `deployProvider`, `activity_sync`, `providers`).
- The root object stays **loose** (`additionalProperties: {}`), matching `worksConfigSchema` being a
  `z.looseObject` (`packages/agent/src/works-config/schema/works-config.schema.ts:376`) and the envelope
  rule "unknown keys are preserved, everywhere" (`works-config.schema.ts:31-36`). Strictness starts at
  `spec` and nowhere above it — CONTRACTS.md C1 says "an unknown key inside `spec`".
- Every object **inside** `spec` is strict _and_ `x-`-exempt:
  `"patternProperties": { "^x-": {} }, "additionalProperties": false`. That is exactly the pair plan.md:162-163
  says the emitter must post-process onto every strict object, and it is what `pos-01` proves.
- `$defs.appSpec` is the spec block on its own, addressed as `app-spec.schema.json#/$defs/appSpec`; the
  root adds `required: ["source"]` on top of it. That split is deliberate and is explained in §4.

Conventions followed from the existing machinery:

| Convention                                                                 | Where it comes from in the repo                        |
| -------------------------------------------------------------------------- | ------------------------------------------------------ |
| draft 2020-12                                                              | `emit-json-schema.ts:50`; `works.v2.schema.json:2`     |
| `$id` under `https://api.ever.works/api/schema/`                           | `emit-json-schema.ts:14`; `schema.md` §25              |
| byte-reproducible, 4-space, trailing newline serialization                 | `emit-json-schema.ts:62-65`                            |
| committed artifact guarded by a drift test                                 | `__tests__/emit-json-schema.spec.ts:69-80`             |

| `Ajv2020` with `{ strict: false, allErrors: true, allowUnionTypes: true }` | `packages/agent-plugins/src/schema-validator.ts:29,53` |
| `oneOf` keyed on `spec.kind` inside the envelope                           | `emit-json-schema.ts:28-47`                            |
| loose objects emitted as `additionalProperties: {}`                        | `works.v2.schema.json:61,67,993`                       |

## 4. The contract changes C1 / C2 / C3

### C1 — strict reporting, with the `x-` exemption

| Requirement (CONTRACTS.md:18-21)                                  | Where it is enforced                                                                                                                                                                     |
| ----------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| An unknown key inside `spec` is an error (`unknown_field`)        | `additionalProperties: false` on all 24 strict objects in `$defs`                                                                                                                        |
| … except keys starting with `x-`                                  | `patternProperties: { "^x-": {} }` on the same 24 objects → **`x-` keys are accepted at any depth**; `pos-01` proves it at `spec`, `source`, `components[0]` and `env[0]`                |

| Two optional keys join `spec`: `kind: app`, `appSpecVersion`      | `#/$defs/appSpec/properties/kind` (`const "app"`, optional) and `.../appSpecVersion` (`integer`, `1..1000`)                                                                              |

properties matched by neither. That is why the exemption cannot be modelled as "allow everything and
warn" — it is exact.

## 7. What is deliberately _not_ in the JSON Schema

The schema is not "the most we could express"; several things are excluded on purpose:

1. **Warnings.** `image_not_pinned` (R19) and `advisory_check` (R20) are _warnings_, and a JSON Schema
   failure has no severity — an editor would show it as an error, and the platform's own rule "a warning
   is shown and the spec still applies" (`schema.md` §0) would be broken. `neg-17` is the fixture that
   keeps them out: three warnings, zero schema failures.
2. **Mode-dependent rules.** `blueprint_mode_forbidden_key` (schema.md §3) depends on _where_ the file is
   being validated, not on its content. A single schema with a `source`/`blueprint` prohibition would
   reject every Blueprint — see `gaps-and-contradictions.md` G1. The stand-alone schema therefore
   exposes `#/$defs/appSpec` **without** the root's `required: ["source"]`, and the mode is applied by
   the caller.
3. **RE2 compatibility** of `validate.pattern`. The schema's own `pattern` keyword is ECMA-262 (Ajv
   compiles with `new RegExp`), so a look-around would validate in the editor and fail on the platform.
   Rather than encode RE2's _absence_ of look-around in ECMA-262 — which would be a claim about a
   different engine — it stays rule-level (`pattern_unsupported`). See `gaps-and-contradictions.md` Q6.
4. **Arithmetic between fields**: R9 (generated length), R17 (limits vs requests), R21 (cron interval),
   and every `MemQuantity`/`CpuQuantity`/`StorageQuantity` _range_. The schema carries the unit
   **syntax** (`^[0-9]+(Mi|Gi)$`) because that is a shape; comparing `1Gi` with `512Mi` means parsing a
   number out of a string, which JSON Schema cannot do.
5. **Set membership against a dynamic list**: `publicBuckets ⊆ buckets` (R14/§11), component and env
   names (R3, R4, R14, R15, R16).
6. **Anything about the file as a file**: the 256 KiB limit, nesting depth 12, YAML alias expansion 100,
   duplicate mapping keys, the 200-issue cap with `truncated` (§2.5). These belong to the text pipeline
   because a JSON Schema is applied _after_ YAML parsing, when the evidence for them is already gone.
7. **Defaults.** The schema documents defaults in `description` but never materialises them, matching
   `schema.md` §0: "Defaults are never written back into the file."

Three things the emitter must do that a hand-written schema gets for free, and that plan.md:162-163
already requires:

1. add `patternProperties: { "^x-": {} }` to **every** object emitted with `additionalProperties: false`
   (zod's `z.strictObject` emits one or the other, never both);
2. emit one `unknown_field` per unrecognised key, not one per object;
3. keep `z.toJSONSchema`'s per-subschema `$schema` noise out of the app branch — the committed
   `works.v2.schema.json` repeats `"$schema"` inside every kind branch (e.g. `works.v2.schema.json:73`),
   which is harmless for Ajv with `strict: false` but is not what a hand-written `$defs` document should
   imitate.

`$defs.appSpec` also gives APW-06's renderer and APW-04's provisioner a stable pointer to validate a
_single spec block_ without the envelope (`app-spec.schema.json#/$defs/appSpec`), which is exactly what
a Blueprint apply or a draft validation holds in memory.
