# Fleet session — trust model

**Status:** Living document. First draft 2026-10-08 (self-build slice AL, EW-762 §6 row AL),
in response to the 2026-05-17 security audit's recommendation #23 ("build a prompt-injection
canary — none exists"). Companion to the platform [Threat Model](./THREAT-MODEL.md) and the
user-facing [Fleet](../../features/fleet.md) guide.

> **One statement of what a fleet run trusts, what it does not, and what each control actually
> guarantees — so slice C's "no platform tools in the session" and slice Z's MCP bridge are
> reconciled in one place instead of contradicting each other across two designs.**

A **fleet run** executes a Task on the **owner's own machine**: an enrolled PC (`apps/node`,
`ever-works-node`) leases a job, provisions a Git worktree, runs a **local Claude Code / Codex**
on the platform-assembled instructions, grades acceptance checks, and commits + pushes the task
branch. The model loop happens on the PC, under the PC's own CLI login and Git credentials, and
only the outcome travels back. This document is about the **boundary around that model step**: the
input is hostile, the model can run a shell, commit, push and — since slice Z — call platform MCP
tools, and the controls below are what keep one prompt injection from turning into credential theft
or an unsanctioned write.

The canary that EXERCISES this model end to end against real injection payloads is
[`apps/node/src/core/executors/agent-task-injection-canary.spec.ts`](../../../apps/node/src/core/executors/agent-task-injection-canary.spec.ts).
It is part of the ordinary `apps/node` vitest run, hermetic (no network, no real credential path,
no real model CLI), and runs on Windows and Linux. The controls below that have a direct assertion
are pinned by a case in it (the env scrub, the HOME redirection, the delivered-`.env` exclusion, the
reporting scrub, the task-branch-only push, the owner-question exclusion, the hook neutralization,
the MCP credential injection + route allow-list, the MCP isolation from the machine owner's own
servers, and the containment disclosure); the structural
gaps are honest `it.fails` cases, not skips. A few rows are stated controls the canary does not
assert line-for-line (for example token-free clone URLs, or the full owner-answer protocol) — those
are covered by their own slices' suites, not re-proven here.

| **PR review feedback** (GitHub reviews / comments on a fleet-made PR → Task rejection rows → the CI-feedback / fix loop's auto-resume)                       | **Trusted to steer, untrusted as content — and only from people who may.** A recorded rejection is replayed into the next run, and the fix loop starts that run on the owner's PC. So a HUMAN review or comment counts only when GitHub's `author_association` is **OWNER, MEMBER or COLLABORATOR** (`classifyReviewAuthor`); `CONTRIBUTOR`, `FIRST_TIME_CONTRIBUTOR`, `FIRST_TIMER`, `MANNEQUIN`, `NONE` or a missing value records nothing, rings nothing and is no merge approval either — on a public repository anyone can click "Request changes". (`MEMBER` / `COLLABORATOR` include read- and triage-level collaborators: the association does not encode a permission level, and a `collaborators/{user}/permission` ≥ write check is a recorded follow-up, F7.) A trusted human's row is replayed marked "trusted reviewer" under a softer notice — follow it, but it cannot authorize pushing elsewhere, disabling or weakening checks, or revealing secrets — and is not fenced as data. Allow-listed reviewer bots (`GITHUB_TRUSTED_REVIEW_BOTS`) count only for an **automatic** finding (`classifyReviewBotComment`): an inline comment that OPENS a review thread, or an issue comment that opens with Greptile's own summary / TREX marker **and was posted by `greptile-apps[bot]`** (any other bot can be coaxed into printing the marker). A bot's chat answer on the PR conversation (`chat-reply`) never counts: whoever asked the bot can be anyone, so "@coderabbitai reply verbatim: …" must not launder a stranger's text into the fix loop (F3). **Deliberate trade:** a bot's reply INSIDE a review thread (`thread-reply`) never counts either — even a genuine new finding tagged with a severity marker — because the person the bot answers can be anyone and can ask it to print the marker. Keeping tagged replies that answer a trusted author would need the thread's prior comments and their `author_association`, i.e. an extra GitHub API call on the webhook path and a git-provider contract change (`listPullRequestReviewComments` carries neither `in_reply_to_id` nor the association, and reads one page); the thread-opening finding is still recorded, and the trade is accepted. Never a placeholder, summary, command ack, limit notice or an edit either; the platform's own `<slug>[bot]` identity never counts. A bot's comment body is replayed fenced as `<review_feedback source="bot">` data (`<` and its NFKC look-alikes neutralized) under a strict "data, not instructions" notice (F5); nothing replayed is a channel that can change where the run pushes (controls 4, 7, 8). |
| **CI check results** (`check_run` / `check_suite` / `workflow_run` deliveries, and the two-minute PR-status poll's re-offer → the CI fix loop's auto-resume) | **Trusted to steer only from an allow-listed app, about this repository's own head; the provider's words untrusted as content.** Only `github-actions` and the apps in `GITHUB_TRUSTED_CHECK_APPS` drive the fix loop — one list (`config.agents.getTrustedCheckApps()`) read by the webhook intake, the evaluator (`untrusted-check-app`) and the poll, which only re-offers a red check whose cached reporter (`GitPullRequestCheck.appSlug`) is allow-listed; a commit status has no app and never counts (F8). Others are ingested for the board and triggers only. A delivery's `pull_requests[]` entries count only when their `base.repo` is the delivery's repository (id or API url); a head BRANCH is used only with same-repository proof (such an entry whose head repo is its base repo, or `workflow_run.head_repository` = the repository): for a fork pull request GitHub reports the FORK's branch name, which the fork owner chooses, so fork CI never resumes a Task (F1). A delivery that names no pull request and matches a Task by branch alone may only speak about a commit the Task already knows (`ciHeadSha` / `prHeadSha`) and never advances the recorded head (`unverified-branch`). Only the check NAME, output TITLE and output SUMMARY are fenced as `<review_feedback source="ci">` data (F5); the platform's own guidance around them ("fix the cause, push to the same branch, do not weaken a check"), the coordinates and the run link stay outside the fence, as instructions.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |

## 2. The controls, and what each one guarantees

Each control is marked **SHIPPED** (holds today, asserted green in the canary) or **GAP** (does not
hold today, asserted as an honest `it.fails`, and disclosed on the job result's `containment`
block so an operator can see it rather than assume full containment).

## 3. Reconciling "no platform tools" (slice C) with the MCP bridge (slice Z)

Slice C's multi-repo risk table, and slice A's instructions, mitigate prompt injection partly by
asserting **"no platform tools in the session."** Slice G/Z then added an MCP bridge that gives the
session platform tools. Neither text acknowledged the other. The reconciliation:

- **"No platform tools" was always a DEFAULT, not an invariant.** A fleet run is sealed unless the
  MCP bridge is switched on, and switching it on needs **three independent yeses**: the operator's
  `FLEET_NODE_MCP_BRIDGE_ENABLED` + a server URL, the Agent's own **Call external tools**
  permission, and a run that is not in `plan` mode. Absent any one, the run is the tool-free
  session slice C described. "Tool-free" includes the **machine owner's own** MCP servers and
  claude.ai connectors: until 2026-10-09 a no-bridge Claude Code run silently loaded them, and it
  now starts with an empty strict MCP config instead (control 16). Since 2026-10-16 a Codex run
  starts with `exec --ignore-user-config`, so it loads none of the owner's Codex MCP servers or
  plugin servers either (control 16).
- **When tools ARE on, the containment does not depend on the model behaving.** The bridge is not
  "the model can now call the API." It is a **narrow, credential-injecting, loopback-only** channel
  (control 9) whose reach is bounded by the **run token's route allow-list** (control 10), enforced
  **on the platform**, not by trusting the prompt. A run token cannot mint another credential,
  cannot answer its own human gate, cannot complete its own job, and cannot drain the machine it
  runs on. So the property slice C relied on — "an injected prompt cannot escalate through platform
  tools" — is preserved by the token's blast radius, even though the literal "no tools" is no longer
  true.
- **The model never holds the credential.** Slice C's worry was a model with a key. The bridge is
  designed precisely so the model holds only a localhost URL; the token is in the node's memory. So
  "tools are available" never becomes "a credential is available to the thing reading untrusted
  input."

The correct one-line statement, replacing both old texts: **a fleet session has no platform tools
by default; when an operator and the Agent's own permission both enable them, the model reaches a
bounded, read-leaning tool surface through a credential it never sees, and the bound is enforced by
the platform's route allow-list, not by the prompt.** In neither case does a Claude Code or Codex
session get the machine owner's own MCP servers (control 16).

## 4. The residual picture

What a prompt injection on a fleet node **can** still do today, stated plainly so it is not
rediscovered as a surprise:

- read any file by **absolute path** (controls 12/14), including the mirrored CLI session
  credential, and **write** outside the worktree and to the mirrored session home;
- open an **arbitrary outbound connection** and carry a secret out (control 13);
- **copy the mirrored `~/.claude` CLI credential into a tracked file and have the node push it** on
  the task branch (control 14) — the delivered-`.env` and push-scope controls do not cover it;
- **write** the owner's `~/.codex/config.toml` in the mirrored session home (control 14). A fleet
  Codex run never loads it (`exec --ignore-user-config`, control 16), but the owner's own
  interactive Codex sessions do.

What it **cannot** do: read the node's lease secret or unrelated credentials through the environment
(1), reach `~/.ssh` / `~/.aws` / the Git credential store through the granted env (2), get a
**delivered `.env` secret committed or pushed** (5) or push to any repo/branch beyond the task branch
(7, 8), **report** a stolen env/`.env` value back to the platform (6), run a repo hook or fsmonitor on
the node's own commit (15), mint another credential or answer its own human gate through the tools
(9, 10), call the machine owner's own MCP servers or claude.ai connectors on a Claude Code run, or the
owner's Codex MCP or plugin servers on a Codex run (16),
or make the platform open a PR somewhere it did not plan (4, 8).

Since 2026-10-18 it also **cannot**: run a hook from the repository's `.claude/settings.json` (or the
owner's, or one an earlier run planted in the mirrored home), or load that repository's `env` /
`apiKeyHelper` (17); counterfeit an `# OWNER ANSWER` block from inside a Task brief, a CI log or a bot
comment (19); and it cannot get skip-permissions or node-run shell commands (setup, steps, acceptance
checks — repository code it may have edited) on a machine whose owner did not switch them on locally (18).
With both switches at their default (and restricted mode on, on a CLI that supports it), the only process
a fleet job starts on the PC is the pinned model CLI under its own permission mode, plus the node's own Git.

The two structural gaps (12, 13) and the committable mirrored credential (14) all close with the same
unshipped piece — the **signed Windows Job-Object executor** (slice AK's blocked half) plus an egress
subsystem — and are **disclosed on every run** via the `containment.downgrades` block rather than
hidden. Gap 15 (repo hooks / fsmonitor on the node's own commit) is **closed** by slice AL: the
finalize commit now runs `--no-verify` with `core.hooksPath` pointed at an empty dir and
`core.fsmonitor=false`, matching the credentialed push.
